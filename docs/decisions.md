# Decisions

Measure-and-decide steps from `PLAN.md`. Each section records the experiment, the numbers, the decision
and its known limits.

## Q1: sync model

### Question

Is full-XML sync (every window sends its whole document after an edit, the host passes it on) good enough
for v1, or does it need operation-level sync? Thresholds from the plan: a lost edit on *different*
elements, or an interrupted in-progress edit in a receiving window, is a defect that must be fixed;
p95 edit-to-visible latency above 500 ms on the large diagram means switching to operation-level sync.

### Experiment

`test/e2e/q1-sync.measure.spec.js` (not part of the regular suite; run with
`BPMN_EDIT_MEASURE=1 BPMN_EDIT_MEASURE_OUT=<dir> npx playwright test q1-sync.measure`). It starts the
real CLI, opens 2 or 3 separate Chrome contexts (1280×800) and makes every edit with the real mouse and
keyboard; state is only read with `page.evaluate`. macOS, Google Chrome via Playwright, everything on
localhost.

- Diagrams: the small fixture `test/fixtures/order.bpmn` (7 flow nodes, 6 flows, 5.6 KB) and a large one
  generated by `scripts/gen-large-bpmn.js` (16 rows × 10 columns: 160 tasks, gateways and events plus
  144 sequence flows = 304 elements with DI, 98 KB).
- Latency: one window drags a shape; time from its `pointerup` to the moment the shape's SVG transform
  changes in each other window (MutationObserver, same machine clock). 20 edits per configuration,
  senders in turn.
- Payload: size of the `update` frame sent and the `remote-update` frame received per edit.
- Lost edits: every window edits a different element and the edits are released together
  (`Promise.all` of the mouse-ups / commit clicks) or, for "staggered", window 2 and 3 release at a random
  0–500 ms offset. 10 rounds each of: moves only (simultaneous), moves only (staggered), one window
  commits a label while the others move. An edit counts as lost if the file on disk does not have it once
  every window is saved and idle; windows are also compared with the file ("disagreements"). Any
  notice shown in these rounds is counted as a false notice (the edits never touch the same element).
- Rapid back-and-forth: two windows alternate 6 moves of different shapes, about 100 ms apart, 5 rounds.
- Delete vs edit: window B has the label editor open on X; window A moves Y, then deletes X; B commits.
  3 rounds. Counted: X back on disk ("resurrected"), A's move of Y gone, a notice shown in B.
- Receiver UX, 3 rounds: viewport (B scrolled) and selection (by id) kept across A's edit; B in the
  middle of a drag while A edits (drag still active after 900 ms and B's move saved); B typing in the
  label editor while A edits (editor still open with the typed text and B's label saved).
- "Stuck" counts a window left with a held-back update that is never shown.

The measurement covers moves, label edits and delete-vs-label only. Concurrent create (palette), append
(context pad), connect, delete, drop onto a flow, and the same-element cases are covered by the
deterministic tests in `test/e2e/q1-concurrency.spec.js` (regular suite), not by counts here:
simultaneous moves in 2 and 3 windows; create + append + delete, then connect + rename + move,
released together in 3 windows; rapid alternating moves and renames; an edit of an element deleted
elsewhere; a move of two shapes, one deleted elsewhere; a move re-applied where someone else just drew a
flow; a drop onto a flow re-applied after someone else's edit; a rename or move accepted just before a
concurrent delete; the same label renamed in two windows (one after the other, and released together);
a drag and a label edit in progress while others edit; viewport and selection; the 304-element diagram
with 3 windows; an edit right before a reload. Several tests hold back one window's outgoing updates
(Playwright `routeWebSocket`, like a slow network) to force a given order at the host, including an
update refused twice: moves of two shapes joined by a flow, one re-applied over the other; deleting an
event whose earlier change was already seen (no notice); a concurrent move of an event that is
deleted (notice with the event's name); a connection to, and a move into a sub-process, deleted
elsewhere (notice names the deleted element); the delete notice and a drop onto a flow after two refusals. Each test ends by checking that every window shows exactly the file on disk (ids,
names, bounds, waypoints).

Notes on the numbers:

- About 300 ms of every latency is the client's send debounce (`SEND_DELAY_MS`); serialising, the
  WebSocket hop and the import take ~15 ms on the small diagram and ~70 ms on the large one. p95 on the
  large diagram is 388 ms, below the 500 ms threshold.
- Before, a simultaneous release of edits on different elements lost one of them in every round (the
  host kept whichever full document arrived last). Staggered releases mostly survived because the
  receiving window rebased its unsent edits; rapid alternation lost edits when two updates crossed at
  the host after a rebase restarted the debounce.
- Before, delete vs edit always brought the deleted element back and also undid the deleting window's
  unrelated move: the failed rebase let the editing window's whole document win, with only a console
  warning.
- In the 3-window small run before the change, windows were left showing something other than the file
  in 3 rounds, and 5 times a window kept a held-back update (notice "Someone else edited; shown after
  your edit") for more than 10 s after everything was saved; in that run 3 of the receiver-UX edits never
  showed up in the receiving window within 5 s. (The first attempt of that run aborted on the same
  condition.) None of this occurred after the change.
- An edit that is refused once (see below) becomes visible to the others after one extra round trip
  plus a re-import and re-apply in the refused window; with 3 windows releasing together on the large
  diagram the last edit was visible everywhere within 2 s in every run of
  `test/e2e/q1-concurrency.spec.js` (asserted there).
- Viewport, selection, an in-progress drag and an open label editor were already preserved before
  (S4); they still are.

### Decision

Keep full-XML transport for v1; make the host the single point of serialisation (optimistic
concurrency) and make the client's rebase op-by-op and safe. Latency does not call for operation-level
sync, but the lost edits and the resurrection are defects that had to be fixed.

How it works now:

- Host (`src/session.js`): an `update` is accepted only if its `baseVersion` is the current version.
  Otherwise the host answers `{ type: 'conflict', version, message }` and changes nothing. The one
  exception is a version that only changes made on disk replaced since: such an update is still accepted
  and replaces the document, with a warning, as before (the disk-race policy is Q2's to decide; see the
  known limits for the case where the disk wins instead). Identical content is a no-op whatever its
  base. *Superseded by Q2: a change on disk now counts like another window's update.*
- Client (`web/app.js`): at most one update in flight. Every user action (root command) is recorded as
  an "edit" of id-based ops: label, move, create (palette, paste), append, connect, delete. Each op also
  records what it expects to find (the label before the edit, the position before the move). The edits
  of the update in flight are kept until the host answers. On `conflict` (or when another window's
  document arrives while edits are unsent) the window shows the newer document, re-applies its edits op
  by op and sends the result right away (no new debounce). Because the host refuses any update not
  based on its current version, two updates can no longer cross and overwrite each other.
- Re-applying an op runs bpmn-js behaviours again, against a document that contains other people's
  changes. Two safeguards keep the result equal to what the original command did:
  - Drop onto a flow (bpmn-js splices a shape moved or created onto a sequence flow into it) only
    happens again into the flow the user originally dropped onto; otherwise it is switched off while
    re-applying. Without this, a move re-applied over someone else's new flow spliced the shape into
    that flow, rewired it and deleted two existing flows.
  - Each re-applied op may change the elements its original command changed (recorded from the
    command stack's dirty list), connections attached to them and, for a re-applied drop onto a flow,
    the new second half of that flow. Elsewhere it may only change geometry of connections (re-layout)
    and external labels (bpmn-js repositions a neighbour's label when a flow is re-laid out). Any
    other change (an element created or removed elsewhere, a connection reconnected, a shape
    re-parented or renamed, another shape moved) means the op is undone and reported (`dropped`
    toast, "…could not be applied on top of someone else's edit"). Splicing into and merging of flows
    are structural and therefore still caught.
- Re-applying runs commands that are recorded as edits again; those are replaced by the original
  edits (narrowed to the ops that applied). So an edit keeps what it expects to find (label before,
  position before, the element as the user saw it when deleting, the flow it was dropped onto) no
  matter how often the host refuses the update and it is re-applied; `overrides` are worked out again
  from that original state on every re-apply.
- An op that cannot be re-applied is dropped on its own and the window shows a toast (`#toast`,
  `data-kind="dropped"`), e.g. "Your change to “Ship order” was not applied: someone else deleted it".
  It names the element that is gone: for a connection the missing end, for a move or create the
  container (sub-process, participant) or host it went into, if that is what was deleted.
  The other ops of the same edit and the other edits are kept (e.g. moving two shapes when one was
  deleted elsewhere still moves the other).
- Same element, same property (label text, position): the first update the host accepts wins. The
  window whose op finds the label or position changed by someone else drops that op and shows a toast
  (`data-kind="conflict"`), "…was not applied: someone else changed it first". Different properties of
  the same element (one window renames, another moves) are both kept.
- Delete vs a concurrent edit of the same element: the delete wins. If the edit is still unsent or
  refused, its window drops it with a `dropped` toast ("…someone else deleted it"). If the edit was
  accepted first and the delete is re-applied over it, the deleting window notices that the element
  changed since the user deleted it (position, size or connection ends, and name, noted just before
  the delete command ran) and sends its ids as `overrides` with the update; the host passes
  them on in `remote-update`, and a window that had that element in an accepted update in the last 30 s
  shows a `conflict` toast ("Your change to “…” was undone: someone else deleted it at the same time").
  A delete that is not concurrent (the deleting window had already seen the edit) reports nothing.
  The same applies to connections: a delete notes the connections attached to the element when the
  user deleted it; a connection someone else added meanwhile (append, connect) that the re-applied
  delete removes is reported to them ("Your connection to “…” was removed: someone else deleted it at
  the same time"; `overrides` entry with `kind: 'connection'`). An appended task itself stays.
- Commands without an op capture (resize, bendpoints, replace/change type, colour, lanes/participants,
  …) and undo/redo of edits already sent are recorded as unsupported edits. They are sent normally; only
  when the host refuses that update are they dropped, with a `dropped` toast, after the newer document is
  shown. They never make this window's whole document replace other people's changes. Undo/redo of
  edits not yet sent simply removes / restores the edit, and an unsupported undo cancels its edit if
  that edit is part of the same rebase.
- A remote document arriving while the user drags, has the label editor open or has a popup menu open
  is held back until that ends (notice "Someone else edited; shown after your edit"), then shown with the
  user's edits re-applied. Viewport and selection (by id) are restored after every import.

Why this and not the alternatives:

- Host-side 3-way merge by element id: needs the base version of every client's update, a BPMN-aware
  merge of semantic elements and DI (references between elements, ordering, labels), and conflict
  rules on the host. More code than the client rebase, and most of it would be replaced by a CRDT later.
- Operation-level sync with bpmn-moddle on the host: moves command semantics (layout, behaviours, label
  placement) to Node, which bpmn-js does not provide headless; the host would either reimplement them or
  need jsdom. Latency does not require it (p95 388 ms on 304 elements, dominated by the debounce).
- The chosen design reuses the existing full-XML protocol (one new message type, one optional field), keeps the host a
  dumb, ordered version store, and confines merge logic to the op capture/re-apply that already
  existed. The recorded ops are also the natural input for the Yjs upgrade path in `bpmn-edit.md`:
  they are already id-based element operations, the mapping to a `Y.Map` of elements needs.

### Known limits

- Undo history is reset whenever another window's document (or a change on disk) is shown, including
  after a rebase. Undo then only covers edits made since.
- Unsupported commands (above) are lost if they race another window's edit (with a toast). So is an op
  whose re-application would touch other elements than the original did (e.g. a drop onto a flow that
  someone else rewired meanwhile).
- Conflict detection covers label text and position only; ops exist only for the commands listed above.
- Changes on disk racing browser edits (Q2): an update based on a version that only disk changes
  replaced overwrites those changes (warning on the host's stderr and in the browser console). The
  other way round also happens: if a change on disk reaches the host while an accepted browser edit is
  still waiting in the host's write debounce (250 ms), the pending write is dropped (`src/file.js`:
  "a pending save from the editor was discarded"), the disk version is pushed to every window and that
  browser edit is lost, with only the stderr warning. So neither side reliably wins today.
  *Resolved by Q2 (below).*
- Closing, reloading or hiding a window sends a pending edit right away instead of after the 300 ms
  debounce (best effort, `beforeunload` / `pagehide` / `visibilitychange`; `beforeunload` for Firefox,
  S10); an edit whose update is still waiting for a rebase at that moment is lost. Since Q2 this
  includes a change on disk that arrived while the edit was still being made: the update sent on
  leaving is based on the version before it and is refused (it is never sent over the change on disk).
  Edits the host had already accepted are not affected (Q2 keeps them aside if a change on disk
  replaces them after the window closed).
- A window that shows another window's document serialises it itself on its next edit; bpmn-js may
  write the DI elements in a different order than the file had, so `git diff` shows reordered lines that
  carry no change.
- Every edit sends the whole document to the host and from the host to every other window (107 KB per
  edit on the 304-element diagram). Fine on localhost; through a tunnel this is the first thing to
  revisit (diffs, or the Yjs path).
- A window whose edits keep being refused (others editing continuously) keeps rebasing; each refusal
  means someone else's edit was accepted, so the session as a whole always progresses.
- After a re-apply, an edit made of several commands (append = create + connect, paste) is tracked
  under the id of its last command, so undoing only part of it right after a re-apply (before it is
  sent, which happens immediately) is not tracked exactly.
- The client relies on diagram-js internals (`commandStack._currentExecution`, `_stack`, `_stackIdx`)
  to find root commands and undone edits; if they change, every edit is treated as unsupported (safe,
  but concurrent edits are then dropped with a toast instead of merged).

## Q2: browser edit racing a save made on disk (IDE)

### Question

What happens when an edit in the browser and a save of a different change by another program (an IDE)
land within the debounce windows, in either order, or just before Ctrl-C? Is anything lost silently,
and what should the policy be? Product preference: never lose work silently.

### Experiment

`test/e2e/q2-ide-race.measure.spec.js`; method, per-trial data and root causes in
`docs/q2-ide-race.md`. Real CLI, two Chrome windows, the fixture in a temp git repo
(`core.autocrlf=false`), the IDE save simulated by reading the file and writing it back with another
element renamed (`fs.writeFile`). Scenarios: (a) browser edit, then IDE save 0–600 ms later, 15 trials;
(b) IDE save, then browser edit 0–400 ms later, 15; (c) IDE save 20–140 ms before the host writes the
accepted edit, 15; (d) IDE save 0–100 ms before SIGINT while the accepted edit waits for its write,
10 (fresh CLI each).

### Results

| | Before: both kept | Before: lost silently | After: both kept | After: lost (silently or not) |
|---|---|---|---|---|
| a | 2/15 | 13/15 (7 browser edits, 6 disk changes) | 15/15 | 0 |
| b | 11/15 | 4/15 (disk change) | 15/15 | 0 |
| c | 0/15 | 15/15 (disk change) | 15/15 | 0 |
| d | 0/10 | 10/10 (disk change) | 10/10 | 0 |

Before, no loss was shown in any window (the only trace: a stderr warning in 14 of the 42 losses); the
windows always agreed with the file, so everyone converged on the smaller document. Four causes: the
store dropped an accepted but unwritten browser edit when a change on disk arrived; the write loop
wrote over a change the watcher had not reported yet (it waits 150 ms for the file to settle); the
session accepted browser documents based on a version a change on disk had replaced (last write
wins); shutdown cancelled the pending check and flushed over the change.

### Decision

**The change on disk is the newer base; browser edits not yet on disk are re-applied on top of it,
per element, with the Q1 machinery. A true same-element conflict keeps the file's version and is
shown in the window whose edit lost. Nothing is ever written over a change on disk the host has not
seen.** Alternatives considered: last write wins with a toast (still loses work, just visibly);
pause-and-ask (a modal in every window for something that is almost always mergeable, and nobody to
ask at shutdown or when the host's window is not focused); disk always wins (loses browser work).

How it works:

- Session (`src/session.js`): a change on disk is a version like any other: an update based on an
  older version is refused (`conflict`), and the window re-applies its edits on top (Q1 rebase). The
  one exception kept from before: a change on disk that the editor cannot display (`import-failed`)
  can still be replaced by an edit based on the version before it (warning on stderr).
- Pre-write check (`src/file.js`): right before the rename that replaces the file, the store compares
  the file with what it last read or wrote: `stat` (inode, size, mtime) as a cheap pre-check, then the
  content. If another program changed it, the temp file is discarded, the write is held back and the
  change is reported after the usual settle delay, exactly like a change the watcher found first.
  If the file was invalid or missing when last seen, the host may still replace it while it stays
  missing or holds exactly the broken content reported after it settled (as before). Anything else
  holds the write back: a complete BPMN document counts as a change made on disk, other content
  means another program is still writing (e.g. truncated and about to be rewritten), so the host
  waits until the file settles (no stat shortcut in that state).
- Slow saves (`src/file.js`, `confirmMs`, 2 s): a write that replaced a missing or invalid file is
  not reported as saved until the file has held our content for 2 s, counted from that first write
  (further writes of ours do not restart it: under continuous editing the wait would never end), and
  restarted by every missing/invalid observation. The file is read when the wait ends; if it does
  not hold our content (the other program broke it again), the write stays unconfirmed for as long
  as that lasts (the windows keep the "not valid BPMN" notice). If a valid save arrives while
  unconfirmed (an IDE finishing a slow save from its own copy, without the browser edit), it is
  treated like a change that replaced a pending write: the edits are re-applied on top of it in their
  windows (merged toast), or kept aside if their window has closed. The windows show "Saved" as soon
  as the host accepted an edit, also while such a write is unconfirmed; the UI does not distinguish
  this (rare) state. A program saving in place through one file descriptor (truncate, write, pause,
  write the rest) writes the rest into the file our rename replaced, not into the file at the path; so
  while unconfirmed, that replaced file is kept open and polled (see "After the merge" below).
- Shutdown while a write is unconfirmed: `flush()` always keeps a copy of it aside (side file +
  stderr), whether or not the file holds it at that moment, because the other program may finish its
  save after we exit (the verifier's "IDE finishes after exit": before 8/8 lost silently, also with a
  second edit still waiting for its write). Chosen over waiting out the rest of the 2 s at shutdown:
  waiting delays Ctrl-C and still loses the edit if the program finishes after the wait (which is
  what happens when it finishes after exit). The cost is a side file nobody needed when no other
  program was involved, only when Ctrl-C comes within 2 s of replacing a broken or deleted file. A
  normal Ctrl-C is neither delayed nor leaves a side file (E2E asserted).
- Re-applying is idempotent (`web/app.js`): a label already at its new text, a created element or
  connection already there, a deleted element already gone, and (new) a moved shape already at its
  target position count as applied. Before, a change on disk that already contained a move (an IDE
  that reloaded the host's write) gave a false "changed on disk" conflict toast. The "merged" toast
  is shown only if something was actually re-applied, so a change on disk that already contains the
  window's edits (moves, appends, connects, deletes, labels) shows no toast at all.
- Merged toasts: they are correct but frequent in long sessions with an IDE saving often (the
  verifier counted 3–5 per window per minute with clean IDE saves of other elements). They could be
  rate-limited or folded into the "Reloaded from disk" notice; left as is for v1 (tunable in
  `reportDiskMerge`, `web/app.js`).
- Replacing the file: right before the rename, the store re-stats the file synchronously and checks
  again if it changed while being checked, so the remaining gap is the rename call itself.
- Unwritten accepted edits: when a change on disk replaces a pending write, the session marks the
  disk version with `discardedAfter` (the last version that is on disk). The host also tells the
  windows when versions are on disk (`saved`), so each window keeps the edits of its acknowledged
  updates until then; on a disk version with `discardedAfter` it re-applies its own edits newer than
  that, before its other unsent edits, and sends the result, saying which of its versions it
  re-applied. Until every window concerned has done so, the host remembers the unsaved document; if
  one of those windows is gone and does not come back within 20 s, or at shutdown, that document is
  saved next to the file (see Shutdown below for the name), with a stderr warning (details in "After
  the merge" below).
- Browser (`web/app.js`): a change on disk is no longer sent over; it is rebased onto like another
  window's edit. Every window shows "Reloaded from disk" as before; the window whose edits were
  re-applied shows a toast (`data-kind="merged"`): "The file was changed on disk; your edits were
  applied on top of that change". Ops that cannot be re-applied are reported with disk wording, e.g.
  "Your change to “Ship order” was not applied: it was changed on disk at the same time (the file's
  version was kept)" (`conflict`), "…it was deleted on disk" (`dropped`). A delete re-applied over an
  element that was changed on disk says so in the deleting window ("Your delete of “…” removed a
  change made to it on disk").
- Shutdown (`bin/bpmn-edit.js`; full order with S7/S8 below): after the windows sent their last edits, the host
  checks the file at once (`session.checkDisk()` → `store.checkNow()`, no settle delay). If a change
  replaced unwritten edits, the windows get it, re-apply and send again (second drain, 1 s max) before
  the final write. If nobody re-applied them (no window left, or the drain timed out), or the file
  changes between that check and the final write, the file keeps its content and the editor's
  version is saved next to it as `<name>.bpmn-edit-unsaved-<yyyymmdd-hhmmss>.bpmn` (shows up in
  `git status`), with a stderr warning naming the file.

Verified by `test/e2e/q2-ide-race.spec.js` (regular suite): accepted edit + IDE save of another
element (both kept in the file, `git diff` and both windows; merged toast); IDE save inside the settle
delay just before the host write, with the file sampled every 5 ms for 2 s to prove it is never
overwritten (`core.autocrlf=input`); browser edit right after an IDE save; same label in both (file
wins, conflict toast with the exact text, file not overwritten later); Ctrl-C right after an IDE save
(both kept, exit 0); Ctrl-C with no window left (file keeps the save, edit kept aside, untracked in
`git status`); a valid save just before the host write after the file was invalid, and after it was
deleted (both kept); a slow save that finishes after the host wrote a browser edit over the
half-written file (both kept, merged toast); Ctrl-C after the slow save broke the file again (file
left alone, edit kept aside); Ctrl-C within 2 s of replacing a half-written file with the IDE
finishing after exit, with and without a second edit waiting for its write (edits kept aside, no
shutdown delay); a normal Ctrl-C (under 1 s, no side file, no warning); a save that already contains
a move made over a broken file (no false conflict toast); a save replacing the unwritten edit of a window that
closed (edit kept aside, file keeps the save). The two S3 tests that asserted last-write-wins now assert that both changes are
kept.

### With reconnect and sharing (S7/S8)

Q2 was developed in parallel with S7 (share, tokens, Host checks) and S8 (keepalive, reconnect,
close 4002) and merged after them. What the merge decided:

- Messages: `saved` and `remote-update` with `discardedAfter` are broadcast like every other sync
  message, i.e. only to sockets that passed S7's Host / Origin / token checks at the upgrade
  (collaborators included: they carry version numbers only, no path or secret). Presence is
  untouched; the socket's `close` handler marks the origin gone (Q2) and leaves the users list (S5).
- One model of pending edits in the page (`web/app.js`), oldest first: `unsavedEdits`
  ([{ version, edits }] acknowledged, not yet confirmed written by `saved`), `lostEdits` (acknowledged
  edits a change on disk replaced before they were written), `inflight` (sent, unanswered) and
  `localEdits` (not sent). The last three are re-applied by one function, `rebaseLocalEdits`, in that
  order, for every cause: a `conflict`, a change on disk with `discardedAfter`, and a reconnect to a
  document that is not the one the edits are based on. An edit is in exactly one of the lists and
  leaves `unsavedEdits` either confirmed (`saved`, dropped for good, never re-applied) or lost (moved to
  `lostEdits`).
- Reconnect: a window that was disconnected misses `saved` and `discardedAfter`, and the host may not
  have noticed the old connection die (so it does not keep the edits aside either). `init` therefore
  carries `instance` (random id of the session; versions only compare within one), `saved` (every
  version up to it is on disk) and `discards` (`[{ after, version }]`: accepted versions in between were
  replaced by the change on disk at `version`; the last 100). On re-sync (`resync` → `reconcileAccepted`)
  the window moves its `unsavedEdits` inside a discard range to `lostEdits` (re-applied, "merged"
  toast and disk wording since the cause was a change on disk), forgets those up to `saved`, and keeps
  the rest waiting (they are in the host's document; a later `discardedAfter` still finds them). With
  another `instance` (bpmn-edit restarted) `unsavedEdits` are forgotten: the old host wrote them or kept
  them aside when it stopped. `lostEdits`, `inflight` and `localEdits` are never written by anyone but
  this window, so they survive any reconnect and are re-applied as in S8.
  So nothing confirmed written is re-applied (no resurrection), nothing is applied twice (an update
  in flight that the host accepted is recognised by its number, see D3 below, or as in S8 by its
  content; re-applied ops are idempotent), and
  offline edits are kept. E2E: `q2-ide-race.spec.js`, "…window that was disconnected: it re-applies it
  on reconnect, with its offline edit" and "an edit already written before the connection dropped is
  not re-applied after a reconnect".
- Shutdown order (`bin/bpmn-edit.js`): stop accepting → drain (windows send their edits) → check the
  file now (`session.checkDisk()`) and, if a change replaced accepted edits, drain again so the windows
  re-apply them → stop watching → `endSession` (4002 to every window) → stop the share and do the final
  write (`store.flush()`, which keeps the editor's version aside if the file changed meanwhile) → exit.
  Why: re-applying needs the windows, collaborators included, so the re-check and its drain come
  before 4002 and before the tunnel stops (stopping the share first would also show "Sharing stopped"
  instead of "Session ended", S8). The watcher is stopped before the windows are closed: a change on
  disk from then on is caught by the final write's own check (file kept, editor's version kept aside)
  instead of a watcher event that would hand edits to windows that are closing (they could not re-apply
  them, and the host would not keep them aside because their sockets were still open). Updates that
  still arrive during `endSession` are accepted and included in the final write. A second Ctrl-C
  keeps S8's fast path (4002 with 200 ms, share stop and flush in parallel, no re-check of the file
  for a last-moment save), but since the fourth check its flush waits for the one the first Ctrl-C
  started, including that flush's last look at the file (`flush()` is single-flight). A third Ctrl-C
  exits at once.
  Since the second check (below), `session.keepUnapplied()` runs after `endSession` and before the
  final write: discarded edits that no window re-applied are kept aside then.

### After the merge: second independent check

An independent check of the merged code (randomised races, reconnects, Ctrl-C, collaborators;
verifier scripts outside the repository) found three silent losses or resurrections. All three now
have E2E regression tests in `test/e2e/q2-ide-race.spec.js` that fail with the fix disabled.

**D1: slow save in place through one file descriptor.** The IDE opens the file for writing
(truncating it), writes half, pauses, writes the rest through the same descriptor and closes. The
host saw the half-written file as invalid and replaced it with a browser edit by rename, so the
rest of the IDE's save went into the replaced, now unlinked file. The file kept the browser edit
only; the IDE's change was gone, with no toast and no side file. Before: 5/5 with a 1.5 s pause,
10 of 30 randomised slow-save trials (30–400 ms pauses); at Ctrl-C the side file lacked the IDE's
change too. Writing by path to finish the save was always fine. Fix (`src/file.js`):
- A write that replaces a missing or broken file opens the file it replaces first (same inode as
  checked) and keeps it open while that write is unconfirmed. The replaced file is polled
  (`fstat` every 50 ms). Once it has changed and then been left alone for the settle delay, it is
  read. If it holds a complete BPMN document, that document is put back in place (renamed in like
  our own writes) and reported as a change on disk that replaced our unconfirmed write
  (`discarded`). The windows re-apply their edits on top of it (merged toast), as for a path save.
- The write is not confirmed while the replaced file is still being written: confirmation waits
  until it has been left alone for `confirmMs` (2 s).
- `checkNow()` (Ctrl-C) and `flush()` read a changed replaced file at once instead of waiting for it
  to settle. At the re-check the windows still re-apply. In the final write the file keeps the
  IDE's save and the editor's version is kept aside.
- Alternative considered: not replacing a broken file until it has been broken and quiet for longer.
  That only moves the threshold (a pause longer than the wait still loses the save) and delays every
  edit made while the file is broken. Watching the replaced file catches the save whatever the
  pause, for as long as the write is unconfirmed.
- After (verifier `g-slowfd`, 5 trials each): one fd, 1.5 s pause: 5/5 both kept; one fd, 250 ms
  pause: 5/5; path finish (control): 5/5; no silent loss. E2E: "a slow save in place through one
  file descriptor, finished after the host replaced the half-written file: both kept" and "Ctrl-C
  right after a slow save finished through the replaced file: both kept". Unit tests: the put-back
  (`discarded`), staying unconfirmed while the replaced file changes, and flush.

**D2: discarded edits of a window that never re-applies them.** Window A's edit was accepted and
waiting for its write. A's connection died without the host noticing, an IDE save replaced the
edit (the host expected A to re-apply it), then A was closed and the host stopped with Ctrl-C. The
edit was gone with no side file; stderr only said "they are re-applied on top of the change". The
side file used to be written only if the origin was already known to be gone at the moment of the
discard. Fix (`src/session.js`):
- Every discard is remembered: the unsaved document plus the versions it replaced, by origin. A
  window that re-applies them says so, either in its next update (`reapplied: [versions]`) or with
  a `reapplied` message when nothing was left to send (all its edits were already in the change on
  disk). Any connection may say so, so a reconnected window counts. Once every version is accounted
  for, the document is dropped.
- If an origin of an unresolved discard is gone (closed, or terminated by the keepalive), the
  document is kept aside after a grace period of 20 s (`REAPPLY_GRACE_MS`;
  `BPMN_EDIT_REAPPLY_GRACE_MS`, hidden, for tests), unless a reconnected window re-applies first.
  At shutdown, after the windows had their chance (both drains, then `endSession`), every unresolved
  discard is kept aside (`keepUnapplied()`).
- stderr names the case: "…changed on disk before the latest edits were saved, and the window that
  made them is disconnected: they are re-applied if it reconnects within 20 s, otherwise the editor's
  version is saved next to the file", or "…the windows that made them re-apply them on top of the
  change" when they are connected.
- The page counts acknowledged edits not yet confirmed written (`unsavedEdits`) as unconfirmed work
  (`hasUnconfirmedWork`): status tooltips while reconnecting or disconnected, and the overlay after
  giving up or a dead link ("Your latest changes may not have been saved."). After 4002 or "Sharing
  stopped" they are not counted: the host writes or keeps aside what it accepted.
- This also settles the redundant side file from the merge (concern 1): a window the host saw
  disconnect before the discard now has 20 s to reconnect and re-apply, and no copy is written then.
- After: verifier `E3` (dead connection, discard, window closed, Ctrl-C): 0/5 silent loss (side file
  with the edit in 5/5); `E1` (host saw the close, window reconnects): 5/5 both in the file, 0
  redundant side files. E2E: "a window whose connection died unnoticed and that closed before
  re-applying: Ctrl-C keeps its discarded edit next to the file" and "a window the host saw
  disconnect re-applies its discarded edit on reconnect: no copy is kept aside".

**D3: resurrection of an update whose ack was lost.** The host accepted and wrote window A's
update, its `ack` was lost with the connection, and the file was then reverted on disk (e.g. by a
checkout). On reconnect A did not know its update had been accepted, so it re-applied it as unsent
work: the rename (and a created task) came back, with no toast. Before: 10/10. Fix:
- The page sends its random key in the WebSocket URL (`?page=`, the same key as presence `hello`) and
  numbers its updates (`seq`). The host remembers, per page key, the newest update it accepted and
  its version (the last 1000 pages), and `init` returns it (`accepted: { seq, version }`).
- On re-sync an update in flight whose `seq` the host accepted becomes an `unsavedEdits` entry at
  that version and is handled like the others: forgotten if written (`saved`), re-applied only if a
  change on disk discarded it. Only updates the host never accepted are re-applied.
- Wording: `init` also carries `lastDisk` / `lastEdit` (newest version from a change on disk / from
  an update). If only changes on disk replaced the window's document while it was away, conflicts in
  its re-applied edits use the disk wording ("…it was changed on disk at the same time (the file's
  version was kept)") instead of "someone else changed it first".
- After: verifier `E2` (ack lost, written, then IDE save of another element / revert of the label /
  revert of a created task / IDE save of the same label): 0/20 resurrected, no toasts. E2E: "an
  update whose ack was lost, written, then reverted on disk while the window was away is not
  re-applied" and "an edit made while disconnected that conflicts with a save on disk is reported
  with the disk wording".

**D4: an IDE save at the same moment as the final write at Ctrl-C** (found while re-measuring with
the verifier's `c-ctrlc` "afterSigint" scenario: IDE save 0–40 ms after SIGINT, edit still waiting for
its write). Before: 1/12 and 2/40 lost one side silently. In one, the IDE's save landed between the
final write's check and its rename, or truncated the file there and wrote the rest into the
replaced file, so the IDE's change was lost. In the other, the IDE renamed its save over ours right
after our final write, so the browser edit was lost. Fix (`src/file.js`):
- The rename is now synchronous (`renameSync`), right after the synchronous re-stat, so no other
  work of ours runs between the last check and the rename.
- Every write keeps the file it replaces open. If that file was written to between the check and
  the rename, the write is treated like one over a broken file (unconfirmed, the replaced file
  polled, a complete save there put back, D1).
- `flush()`: a file replaced less than 300 ms ago is watched until then, and while it is being
  written (at most 1 s), so a save already under way is put back and ours kept aside. If our last
  write is less than 300 ms old, the file is read once more when those 300 ms are up. If it now
  holds another program's save made from a copy older than our write (`containsChanges`, see the
  third check below for how that is judged), the file keeps that save, ours is kept aside, and stderr
  says "another program saved … right after the editor's last save, from a copy without the editor's
  last changes". A save that contains our change keeps nothing aside.
- Cost: Ctrl-C takes up to 300 ms longer when it writes edits or comes within 300 ms of a write;
  otherwise there is no delay.
- After: 40/40 with no loss and no redundant side file (15 kept aside, every one named on stderr;
  exit within 343 ms). Unit tests: stale save right after the last write (kept aside), save that
  contains it (nothing kept), `containsChanges`. E2E: "a save from a stale copy right after the
  final write at Ctrl-C: the file keeps it, the edit is kept next to it".

Re-run of the verifier's other scenarios on the final code (12 trials each unless noted). Races a/b/c
(`autocrlf` false and input) and d: 84/84 both changes on disk, no loss, no side file, windows equal
the file. Reconnect: 12/12. Ctrl-C "reapply": 12/12 both kept. Ctrl-C "closedWindow": 12/12 file keeps
the save, edit kept aside and named. Collaborator: 24/24, no leaks, presence always 2. Slow save
through one descriptor (`g-slowfd`): 15/15 both kept. `e-concerns`: 0 resurrected in 20, 0 silent loss
in 5, 0 redundant side files in 5.

### Third independent check

A fresh verifier (adversarial probes `x-adv`, `y-adv`, `z-adv`, scripts outside the repository) found
two silent losses and a protocol weakness. While re-measuring, two more Ctrl-C cases showed up. Each
fix has a regression test that fails with the fix disabled.

**DEF-1: a delete came back through a stale save at Ctrl-C.** The file was in the editor's own
formatting and a delete was waiting for its write. At SIGINT an IDE whose copy predated the delete
wrote it back 80–290 ms after the final write. `containsChanges` (D4) only checked that the lines our
write added were still there; a delete adds none, so the stale save passed for a fresh one. The
element came back, with no side file and no stderr line. Before: 10/10 (`x-adv` X2, delete).
- Fix: `containsChanges` compares line counts (trimmed lines as multisets). Every line our write
  has more often than the version it replaced must be in the new save at least that often. Every
  line it has less often (removed) must be there at most as often as in our write.
- At the 300 ms re-check, a file that is not complete BPMN, or still changing, is waited for (left
  alone for 50 ms, at most 1 s more) before it is judged. Before, two half-written saves that then
  finished with our edit gave redundant side files and a misleading "the file keeps that save".
  If the file is still being written at the deadline, ours is kept aside with "another program was
  still writing … when bpmn-edit stopped".
- After: X2 delete 0/10 lost, 10/10 kept aside. X2 rename: 2/10 lost, and only where the IDE wrote
  314–344 ms after SIGINT, i.e. after the re-check or after exit (the stale-copy limit below);
  every save inside the window was caught. `c-ctrlc` afterSigint: 0/12 lost, 0 redundant side
  files (before 2/12 redundant).
- Tests: E2E "a stale save right after the final write at Ctrl-C that brings a deleted element
  back: the delete is kept next to the file". Unit: `containsChanges` with a delete; flush with a
  stale save that restores a removed task; flush waiting for a half-written save that then contains
  our change (nothing kept aside).

**DEF-2: a write that found the file missing was confirmed at once.** The file was removed (`rm`,
or renamed away by a vim-style save) 30–240 ms before the host's write, before the watcher had
reported it. The pre-write check treats a missing file as "recreate it", but the write was then
confirmed like any other. When the program that removed it wrote its copy (read before the
removal) 60–360 ms later, the browser edit was replaced silently. Before: `y-adv`
rmJustBefore 10/10, rmLongBefore 10/10, vim-like 1/10; `x-adv` X6 (delete, recreate 50–400 ms
later) 1/5.
- Fix (`src/file.js`): `writeAtomically` reports that the target was missing at the check, and such
  a write is unconfirmed for `confirmMs` (2 s) like one over a broken file. A save arriving
  meanwhile replaces it as `discarded`, and the windows re-apply the edit on top. In the vim case the
  new file is written by path after our rename, so the watcher sees it as such a save.
- After: rmJustBefore 10/10 both kept, rmLongBefore 10/10, vim-like 10/10, X6 recreate 5/5; no side
  files.
- Tests: E2E "the file deleted just before the host writes, then saved from an older copy: the
  edit is re-applied on top". Unit: a write that finds the file missing stays unconfirmed and a
  later save is reported as replacing it; it is confirmed after `confirmMs` otherwise.

**DEF-3: any connection could send `reapplied` for versions it does not own.** A collaborator socket
sending `{"type":"reapplied","versions":[1..200]}` cleared the pending discard of another window's
edit, so no side file was written at Ctrl-C. Before: 3/3 lost (`x-adv` X4b).
- Fix: the page key from the WebSocket URL is scoped by how the socket connected,
  `role:token|key`, as presence scopes its keys. That scoped key is the `owner` of every accepted
  update (`Session.applyUpdate`) and the key of `acceptedByPage` (D3). `reapplied`, as a message or
  on an update, only clears versions in a pending discard whose owner is the same scoped key. A
  reconnecting page (same key, same role and token) still clears its own; a collaborator cannot
  claim the host's or another link's page. Versions not awaiting re-apply are ignored. A connection
  without a valid key can no longer clear anything.
- After: X4b with spoofing 0/3 lost (side file with the edit 3/3).
- Tests: E2E "a collaborator claiming another window's discarded versions does not stop them from
  being kept aside" (the collaborator even uses the window's own page key). Unit: `reapplied`
  without an owner, or with the same key in another scope, is ignored; a reconnected page with the
  same scoped key counts.

**Ctrl-C while another program is rewriting the file** (found re-running `z-adv` Z2 and `c-ctrlc`
afterSigint on the fixes above).
- An IDE began a slow in-place save from an older copy after our edit was already written. Ctrl-C
  came while the file was half-written, and the IDE finished after exit. Nothing was pending, so

  - Fix: if the file was seen newly broken or newly missing after our last write and less than

  - Fix: `flush({ final: true })` (only the CLI's shutdown) leaves a file that became broken or
    disappeared less than `confirmMs` ago to the program rewriting it. The pending edits are kept
    aside ("another program is rewriting … bpmn-edit left it alone").
- After: Z2 by path 0/10 lost (side file with the edit 10/10); afterSigint 0/12 lost.
- Tests: E2E "Ctrl-C while another program is rewriting the file from an older copy: the written
  edit is kept next to it" and "Ctrl-C while another program has just begun a slow in-place save:
  the file is left to it, the edit is kept next to it".

Re-run of every scenario on the final code: races a–d in 5 save modes (in place, temp + rename,

A fourth verifier (probes `n-adv` N1–N8, outside the repository) confirmed the earlier fixes, the

**N2-1: a second Ctrl-C defeated the final stale-save check** (MUST).

- After: N2 staleLate 0/10 lost (side file 10/10), stale 0/10, none / ideBefore / slowfd 0/10 each;

**Docs: stale-copy frequency and the formatting false positive** (MUST).

- The false positive: a fresh save reformatted by another program within 300 ms of Ctrl-C (attribute

- Unit test: `containsChanges` with reformatted fresh and stale copies.

**R1: a slow save through one descriptor still under way at Ctrl-C** (SHOULD, implemented).

  unlinked file after exit. Before: Z2 by descriptor 7/10 IDE changes lost.
- Fix:
  - Right before the rename that replaces a broken file, the file gets a second name, a hard link
    `<name>.bpmn-edit-replaced-<time>.bpmn`. It is made synchronously, checked to be the same inode
    as the file that was checked, and made before the rename because macOS cannot link an open,
    unlinked file.
  - The link is removed when the write is confirmed, when a save found there is put back, when a save
    by path replaces the unconfirmed write, and on every error path.
  - At shutdown with the write still unconfirmed, the link is kept and named on stderr. A program
    still writing through its descriptor finishes its save there.
  - In normal use the link exists only during the 2 s after a write over a broken file.
- Cost: a Ctrl-C within 2 s of replacing a broken file leaves this second file even when nobody was
  writing into it. The host cannot know whether someone has the file open.
- After: Z2 by descriptor 0/10 IDE changes lost (in the kept file) and edits kept 10/10; Z2 by path

- Tests:
  - e2e: "Ctrl-C while a slow save through one descriptor is still under way: its save ends up in the

  - unit: the link is removed on confirm, on put-back and on a save by path; flush keeps it.
  - The three e2e Ctrl-C tests that counted side files now count the editor's side file and the kept

**R2: a save from a stale copy during the session** (SHOULD, conservative variant).
- Before: X3 5/10 browser edits lost silently.
- Fix (`inspectDisk`): a change on disk that replaced no pending write, within 5 s of our last write
  (`STALE_SAVE_MS`), is tested with `looksStale(save, before, ours)`. It is stale if a line our write
  removed is back (the old label, a deleted element), or, for a write that only added lines, none of
  them is there. A later change of the same lines (someone renaming the same element again from our
  version) does not count, unlike `!containsChanges`. If stale:
  - the save is still taken as the newer version (it may be deliberate);
  - our version is kept aside (stderr "…was saved on disk from a copy without the editor's last

  - every window gets `kept-aside` (reason `stale-save`, file name only) and shows "The file was

  - X3 4/10 edits replaced on disk, 0 silently: all 4 kept aside, with a notice.

  - Deliberate reverts within 5 s give the expected visible notice: X7 checkout 4/10 side files.
- Tests:
  - e2e: "a save from an older copy during the session: the file keeps it, the edit is kept next to

  - unit: `looksStale`; the store reports a stale save (reason `stale`) but not a fresh one.
  - Changed e2e: "an update whose ack was lost, written, then reverted on disk while the window was

### Fifth independent check

A fifth verifier (probes `r4-adv`, `chain`, `fp`, `r2m`, `r4c`, `long`, outside the repository)
confirmed the merge: 350 race trials, Ctrl-C single, double, triple and SIGTERM, collaborators, a
200 s session and the R1 lifecycle with unusual file names. It found three silent losses and one
class of false positives in the round-4 code. Each fix below has e2e tests that fail on the round-4
code (checked by running them against it) or with the fix disabled.

**DEF-A: a second browser edit stopped the watch of the replaced file.** While a write over a
half-written file was unconfirmed (its replaced file watched, D1), a second browser edit was
written normally. That write closed its own replaced file through `stopWatchingReplaced`, whose
`clearInterval` was global, so polling of the first write's replaced file stopped. The IDE's rest,
written through its descriptor, was then lost, and the link removed at confirm. Before: `r4-adv` P2
5/5 IDE changes lost silently.
- Fix: a normal write closes only its own handle (and link). `stopWatchingReplaced` stops polling
  only when the unconfirmed write has nothing left to watch.
- After: P2 0/5 lost, no stray files.
- Tests: e2e "a slow save through one descriptor, with a second browser edit while the first write
  is unconfirmed: all kept". Unit: "a normal write during an unconfirmed one keeps the replaced file
  of the unconfirmed write watched".

**DEF-B: a stale save was not checked when it also replaced a pending write.** The check ran only
for changes on disk that discarded nothing. With another edit waiting for its write, the windows
re-applied only that pending edit, and the already written edit was gone, shown with a "merged"
notice. Before: `r4-adv` P1 10/10 lost, silently 6/10 (pending edit in the same window) and 2/10
(another window).
- Fix: the check runs in both cases. Variant chosen: the pending edits are re-applied on top of the
  save as usual (they were never on disk). The written ones are not, because they were confirmed
  and the windows no longer hold them as unsaved. The side file holds the latest version, pending
  edits included. The change carries `stale: true` (`remote-update` too), so the windows skip the
  "merged" notice. They show only the older-copy notice, which names the side file. This keeps one
  outcome for the user: the file has the other program's save plus the edits that were not written
  yet, and everything else is in the named side file.
- After: P1 0/30 lost silently, written edit kept aside 30/30, notice in every trial.
- Tests: e2e "a save from an older copy while another edit waits for its write: the written edit is
  kept aside, the pending one re-applied" (no "merged" notice). Unit: "a stale save that also
  replaces a pending write: kept aside with the pending content, flagged stale and discarded".

**DEF-C: only the last write was compared.** Two writes of the same element in a row (add a task,
then name it; rename, then correct the name), then a save from a copy older than both. The check
compared the save with the write just before the last one, which already had the element: no
notice. Before: `chain` addThenName 10/10 and renameTwice 10/10 lost silently.
- Fix: our writes less than `STALE_SAVE_MS` (5 s) apart, with no other program's change in between,
  form a chain. The save is compared with the disk version before the chain's first write
  (`chainBase`), and the chain's earlier writes are kept (`chainWrites`, last 20). A save in which an
  element we changed has its base form, or its form after one of the earlier writes (a copy from
  between our writes), is old.
- Found while measuring: comparing only with the chain's base made such in-between copies look like
  concurrent changes (`x-adv` X3 2/10 silent).
- After: renameTwice 0/10 lost (kept aside 10/10); X3 0/20 silent (4 replaced, all kept aside with a
  notice); `chain` addThenName could not be re-measured: from its second trial on, the probe's
  palette drag lands on the notice now shown at the bottom of the window. The e2e test covers it.
- Tests: e2e "a save from a copy older than the last of two consecutive writes" (renameTwice,
  addThenName, copyBetween). Unit: `looksStale` with a chain history, and a store-level chain test.

**DEF-D: false positives from lines without ids.** A browser delete, then within 5 s a fresh save
that adds an element, gave a wrong notice and side file: the line multiset counted lines such as
`</bpmndi:BPMNShape>` and `<dc:Bounds …>`. Before: `fp` add 10/10 false positives.
- Fix: element-level comparison by id (`src/elements.js`, used by both `looksStale` and
  `containsChanges`; no new dependency).
  - A small tokenizer reads each document into id -> canonical form: name, sorted attributes,
    trimmed text, and the forms of child elements without an id (bounds, waypoints, incoming,
    outgoing, conditions, documentation) folded into the parent. Children with an id are elements
    of their own.
  - CRLF, indentation, attribute order and self-closing tags do not change any form; namespace
    prefixes are taken as they are.
  - A document that cannot be read counts as old (copy kept).
  - Our changes are the ids whose form differs between the chain base and our last write.
  - `looksStale`: some such id has a form we no longer have (base or in between) in the save. An
    element the other program changed its own way is concurrent, not old.
  - `containsChanges`, used at Ctrl-C where nobody can be told any more, is stricter: every such id
    must have our form. A concurrent change of the same element there also keeps a copy.
- After: `fp` add / remove / other 0/30 side files; N1 (formatting at Ctrl-C) 0 false positives in
  28 fresh trials, 0 silent loss in 24 stale ones; `r2m` fresh 0 side files in 47 completed trials,
  stale 56/56 kept aside; long session (203 edits, 32 IDE saves) 0 notices, 0 side files.
- Tests: e2e "a delete, then a save from a fresh copy that adds an element: no stale notice". Unit:
  element-level `containsChanges` and `looksStale` (reformatting, renamed again, delete, addition,
  unreadable document).

### After landing on main: DEF-E1

**DEF-E1: a save from an older copy that also changed the element we changed was not noticed.** A
task renamed in the browser, written; 0.2–2.5 s later an IDE saves the copy it read before that
write, with its own change to the same task (added `<bpmn:documentation>`, or a new
`<bpmn:outgoing>`). `looksStale` compared whole elements: the task's form in the save was neither
its base form nor ours, so it counted as a concurrent change. The file kept the save with the old
name, the windows showed only "Reloaded from disk", and the rename was gone (10/10, silently).
- Fix (`src/elements.js`, `looksStale`): for an element the save changed in its own way, its parts
  are compared too: each attribute (the element name included) and each child without an id
  (bounds, waypoints, incoming / outgoing, documentation, …, as a multiset). The save is old if a
  part our writes changed has the value (or count) it had before our latest write, i.e. in the
  chain's base or in one of our earlier writes, and not ours. A part changed by the other program
  only, or a part we changed that it changed again to something else (renamed again), still makes a
  concurrent change. Elements with a duplicate id are compared as a whole, as before.
  `containsChanges` (Ctrl-C) already caught this case.
- Policy: unchanged, the stale-save branch of R2 / DEF-B. The file keeps the save (it may be
  deliberate, and it carries the other program's own change), our latest version is kept next to it

  the reason given in R2 (it would undo deliberate reverts).

### Known limits

- The pre-write check and the rename are separate steps. A save renamed over the file between the
  last check (a synchronous stat) and our (synchronous) rename is overwritten, and the watcher then
  reads our content and reports nothing. The gap is two system calls, but it grows under heavy load
  (before the re-stat was added, a verifier run lost one IDE save in 20 heavily loaded
  "invalid/valid flip" trials this way, with the gap spanning a whole file read). An in-place save
  that truncates the file in that gap is caught (D4).
- A broken file that has been quiet for the settle delay is replaced by the next browser edit, as
  before. If the program that broke it then leaves our content alone for 2 s (`confirmMs`) and only
  afterwards finishes its save from its own copy, that save replaces the browser edit like any save of
  a stale copy: every window reloads it ("Reloaded from disk") but nobody is told the edit is gone
  (verifier: 4/4 with the IDE finishing 2.5 s after the host's write). While the file stays broken
  (or is broken again) the write is not confirmed, so that case is merged or kept aside. In short:
  an IDE finishing a save later than `confirmMs` after our first write over its broken file, with the
  file left alone meanwhile, is not detected during the session; at shutdown within that window the
  edit is kept aside.
- A save that is valid for less than the settle delay plus the watcher's latency (about 150 ms plus
  a few ms to tens of ms) before the same program breaks the file
  again is never seen by the host. When the host then replaces the broken file it writes its last
  known valid version plus the browser edits, so `git diff` briefly lacks that short-lived save
  until the program saves again (seen in 1–3 of 10 rapid "invalid/valid" flip trials; the final file
  had everything every time).
- With edits in two windows, a window re-applying an op on an element another window created (and
  has not re-created yet on top of the change on disk) is told the element was "deleted on disk";
  the wording is wrong in that case (inferred from the code, not reproduced).
- Edits of a window that closed after its update was accepted but before it was written are not
  merged: the file keeps the change on disk and the unsaved document (all windows' unsaved edits) is
  kept aside, reported on stderr only (no window of its author is left to show a toast). This
  happens 20 s after the host notices the window is gone (for a connection that died silently, the
  keepalive notices within 30–60 s), or at Ctrl-C. A window that reconnects after those 20 s still
  re-applies its edits, so the side file is redundant in that case.
- A slow save through one file descriptor (D1 above) is caught only while our write over the broken
  file is unconfirmed: if the program pauses for longer than `confirmMs` (2 s) after its last write
  into the replaced file before finishing, or never writes there again after our rename until then,
  its save is lost as in the limit above. If the host is stopped while the program is still writing
  into the replaced file, its save ends up in the kept `….bpmn-edit-replaced-….bpmn` (fourth check,
  R1), not in the file itself: the user has to look there.
- The host remembers only the newest accepted update per page and only for the last 1000 pages; an
  older page key falls back to S8's behaviour (the update in flight is re-applied).
- An update in flight whose page reconnects to a restarted host (another `instance`) is re-applied
  unless the new document equals it (S8): the old host wrote or kept aside what it had accepted, but
  the page cannot tell which.
- If several windows edited while a window was away, its conflicts use the generic wording even when
  the conflicting change came from disk.
- A change on disk is merged only where Q1 has ops (label, move, create, append, connect, delete);
  other browser edits racing it (resize, bendpoints, type change, …) are dropped with a toast.
- Conflict detection is per property (label text, position) as in Q1; a change on disk to other
  attributes of an element the browser edits at the same time is kept (the browser op only touches
  its own property), but the browser cannot report it.
- A save from a stale copy: another program reads the file, bpmn-edit writes a browser edit, and the
  program later writes its older copy back (an IDE buffer loaded before the edit reached the file,
  saved without reloading). That save is newer on disk and replaces the edit. How often this happens
  depends only on the timing of the other program's read and write (verifiers saw 2 to 5 of 10 with
  30–400 ms between them). Since the fourth check (R2, element level since the fifth), such a save
  within 5 s of our last write is noticed if an element our recent writes changed has a form it had
  before the last of them: the file keeps it, the edits are saved next to it, and every window is told
  (a window that was away when it reconnects). Not noticed: a stale save later than 5 s after our
  last write, after a write that replaced a broken or missing file (nothing to compare with), or after
  exit (at Ctrl-C the file is looked at once more 300 ms after the last write). The host cannot tell a stale save from a deliberate one: a revert or `git checkout` within
  5 s of an edit also gets the notice and a side file (visible, never a loss). The editor's undo
  cannot help (its history is reset when a change on disk is shown); git or the other program's undo
  or local history can.
- The stale-save checks compare elements by id (src/elements.js), not text: attribute values and text
  are compared as written, so a program that rewrites them in another form (other character escapes,
  reflowed documentation) makes those elements look changed. During the session that can only hide a
  change as "concurrent" when that element was also changed by us; at Ctrl-C (where an element the
  other program changed again also counts as not having our change) it gives a redundant side file.
  A document the tokenizer cannot read counts as an old copy (a copy is kept rather than guessed).
- Kept-aside files are never cleaned up automatically; that is deliberate (they are the user's work).

## Q3: persistent session links across restarts

### Question

Should a shared link survive a restart of the CLI or a new Share (which needs a stable hostname and a
session token that outlives the process), or is a new link per share acceptable for v1? And how quickly and
how reliably does a Cloudflare quick tunnel come up and stay up?

### Experiment

`scripts/measure-tunnel.js` (full write-up and raw logs: `docs/q3-tunnel-measurements.md`,
`docs/q3-tunnel-evidence/`). The real CLI on a copy of `test/fixtures/order.bpmn`, a quick tunnel from
`src/tunnel.js` pointed at it, one GET of `/` every 20 s for 31 min, a WebSocket held open without sending
anything, Chrome loads at start and end; then the tunnel was stopped together with the CLI, the old URL
probed for 2 min, and after 150 s a second CLI + tunnel started on the same file and port. macOS (M1 Pro),
cloudflared 2026.10.0, Chrome 155. Three tunnels in total (one from an independent verification run), no
rate limiting.

### Results

| | |
|---|---|
| Startup, cached binary (spawn → first HTTP 200) | 6479 / 6849 / 7054 ms; ~5–5.6 s of it is cloudflared obtaining the tunnel |
| HTTP over 31 min | 93/93 × 200, latency p95 101 ms, no cloudflared reconnects |
| Idle WebSocket | cut after 125.08–125.12 s every time (close 1006), 14 times in 31 min |
| Old URL after stop | HTTP 530 / Cloudflare error 1033 from the first probe (1.6 s) for at least 2.6 min; the hostname keeps resolving |
| Restart / re-share | a different random hostname every time; nothing points from the old link to the new one |
| Stable hostname | needs a named Cloudflare Tunnel: a Cloudflare account, an own domain on Cloudflare, `cloudflared tunnel login` or a dashboard token, a DNS route |

### Decision

Persistent links are out of scope for v1. A quick tunnel gets a new hostname on every start, so every
Share (and every CLI restart) gives a new link, and the old one stops working at once (Cloudflare error
1033, which bpmn-edit cannot customise). The README (S9) has to say so: collaborators need the new link.

Why: the only way to a stable hostname is a named tunnel, which needs the user's own Cloudflare account and
domain plus a browser login or dashboard token, so `npx bpmn-edit` cannot set it up for anyone, and the
session token in `/s/<token>` would also have to be persisted across restarts. If ever wanted, it is a
separate opt-in feature (e.g. a `--tunnel-token` option running `cloudflared tunnel run --token`), not
something to block v1 on. Within one run the quick tunnel's HTTP path was stable, which is what v1 needs.

What does have to change, independent of persistent links: an idle WebSocket through the tunnel is cut
after ~125 s, and the page does not reconnect, so an idle collaborator silently stops syncing. The server
must send a keepalive well below 125 s (e.g. every 30 s) and the page must reconnect with backoff and
re-sync; both are handled in S8, with an E2E check that a socket idle for more than 125 s through a real
tunnel stays connected (or recovers transparently). S7 wires sharing up without keepalive.

### Known limits

- The numbers come from one machine on one network over one afternoon; quick tunnels have no uptime
  guarantee ("for testing and development"), and Cloudflare rate-limits their creation per IP (HTTP 429;
  ~5 in a burst locked tunnels out for more than 35 min). The Share UI reports this as such and lets the
  user retry; it never retries on its own.
- Quick tunnels allow at most 200 in-flight requests and no Server-Sent Events (bpmn-edit uses neither).
- The 125 s cut is attributed to Cloudflare's proxy read timeout by the matching number only.

## Q4-impl: saves keep the file's own text (minimal-diff writer)

### Question

Q4 (`docs/q4-diff-churn.md`) measured that the first save of a file made by another tool rewrites it in
bpmn-js's formatting (3–898 lines unrelated to a one-word rename) and silently drops comments, processing
instructions and the DOCTYPE (an entity turned into literal text). It recommended option (c): a host-side
3-way writer that patches only what changed into the text on disk, checked on every write, with a
format-preserving fallback. This step implements it and verifies it against the Q4 acceptance criteria.

### What was built

- **`src/minimal-diff.js`** (no dependencies). A small strict XML reader (anything it does not understand —
  malformed markup, unbound prefixes, duplicate ids — is an error, which only means a fallback; entity
  references are kept as references, like bpmn-js keeps them as text, so DOCTYPE entities from the internal
  subset or an external DTD both work), and `renderForDisk({ disk, base, out })`:
  - `disk`: the text on disk; `base`: bpmn-js's serialisation of exactly that text; `out`: bpmn-js's
    serialisation after the edit (the update the browser sent).
  - Elements are matched by id; elements without an id by position among same-named siblings under their
    nearest element with an id, aligned by content (LCS) so that removing one `<outgoing>` removes that
    line. Changed attributes and texts are patched in place (in the attribute's own quotes; references to
    the file's entities written back as references), removed elements are cut with their line, added
    elements are inserted next to their nearest sibling on disk. Everything else stays byte for byte.
  - **Every element that keeps its id keeps its own text.** Moved to another parent (e.g. dragged into a
    sub-process, also one created in the same save): its text on disk, with the changes inside it
    patched, is cut and inserted at the new place, re-indented. Replaced by another type (the wrench; same
    id): the tags get the new name and the content is patched like any other element; extensions bpmn-js
    drops on replace (attributes and elements in namespaces it does not know, `extensionElements`) stay
    on disk. The DI shape or edge that bpmn-js re-creates with a new id on replace is matched to the old
    one (same `bpmnElement`, same plane) and patched in place (its id changes). So comments, PIs, CDATA,
    entity references and extensions inside moved or replaced elements stay where they were.
  - New elements are rendered in the file's style, detected from the file: line ending, indent unit,
    quote, `/>` or ` />`, attribute layout (one line, one per line aligned under the first, or with a
    hanging indent), and the file's namespace prefixes (a namespace bpmn-js writes as `bpmn:` is written
    with the file's `bpmn2:` or as its default namespace; a namespace the file lacks, e.g. `bioc:` for a
    colour, is declared where bpmn-js declared it, else on the root — only when something written needs it).
  - bpmn-js's empty `<bpmndi:BPMNLabel />` (added to a shape when its label is edited, no information) is
    neither written nor compared, so a rename is exactly one changed line.
  - **DI that bpmn-js moved on import.** bpmn-js ≥ 9 moves the DI of a collapsed sub-process into a
    diagram of its own, with other coordinates. A shape or edge whose coordinates on disk are bpmn-js's
    moved by one constant offset gets bpmn-js's changes (a move, a new label) moved back by that offset;
    the diagram bpmn-js made exists only in its view and is not written. Any other value bpmn-js changed
    whose text on disk differs from the base (beyond number spelling) is refused (fallback) instead of
    written relative to the wrong thing.
- **Labels in collapsed sub-processes of older files (`web/app.js`).** bpmn-js 18's
  `SubprocessCompatibility` moves such DI into a diagram of its own and shifts shapes and waypoints next
  to the origin, but not label bounds, so every label there showed far from its element (in old files
  already, before any edit). bpmn-edit's import now shifts each such label by its element's shift (a
  listener before and after bpmn-js's, priorities 1600 / 1400 on `import.render.start`). With that,
  the labels have the same offset as their shapes, and the writer writes them in the file's own
  coordinates. Why the file's coordinates and not bpmn-js's shifted ones: BPMN DI coordinates are
  absolute in the diagram that holds them (here the main one, as on disk); written that way, the file
  stays consistent with its own shapes and its other labels, renders right in tools that read DI as
  written (bpmn-js < 9 and non-bpmn-js tools), and in bpmn-edit before and after reopening. Writing the
  shifted values instead would misplace the labels everywhere except in unpatched bpmn-js ≥ 9, which
  misplaces all the file's existing labels anyway (its bug); those tools show new labels displaced the
  same way as the file's old ones.
- **Undo of a delete or a type change.** The store keeps (for the run) the text of every element with an
  id that a write cut from the file, with bpmn-js's model of it at that moment (up to 5 versions per
  id, 200 ids). When bpmn-js brings an element back with exactly such a model (undo), that text is
  written back (comments, PIs, CDATA, extensions kept on an earlier type change — bpmn-js's model then
  lacked them, and that model is what is matched), next to its old neighbour on disk; elements cut
  together (a task with its flows and their DI) go back next to each other in their old order. An
  element bpmn-js brings back with another model (e.g. undo re-adds its flow references in another
  order, or drops `sourceElement` on an edge) gets its remembered text back first, with bpmn-js's text
  of it at delete time as its base, and then only what bpmn-js changed is patched in (verifier round 4:
  before, such an element was written from bpmn-js's output and lost its comments, PIs, CDATA and kept
  extensions without a note). Should a remembered element still be written from bpmn-js's output (its
  parent gone, namespaces changed), what that loses of its remembered text is reported (`lost=`,
  warning) even in a `minimal` write. Children only the disk has (extensions kept on
  a type change) are taken for the ones bpmn-js brings back when they are equal, instead of a second
  copy. The check compares restored text with the remembered text: everything in it exactly, every
  element bpmn-js has present, the parent as bpmn-js has it.
- **Namespaces declared per element.** Where a file declares a namespace on the elements themselves
  (`<Bounds xmlns="…/DC" …/>`, Bizagi) rather than with a prefix on the root, new elements do the same
  (the declaration where the file puts it, here last), so the root start tag is not touched.
- **The check (every write).** The result is parsed again and its model compared fact by fact (elements,
  parents, attributes with namespace URIs, xsi:type as a QName, texts, CDATA, comments, PIs, declaration,
  DOCTYPE; an entity reference is a fact of its own, never equal to the literal text `&amp;name;`): what
  bpmn-js changed (`base → out`) must be in the result with `out`'s value (layout moved back by an import
  offset, see above), elements bpmn-js removed must be gone (except the extensions of a replaced element),
  comments/PIs/CDATA/declaration/DOCTYPE of everything on disk must be as on disk — inside moved and
  replaced elements too — and every other fact exactly as on disk. A
  second opinion with an independent tokenizer (`src/elements.js` element forms): every element the
  result changed compared with the disk must be one bpmn-js changed. Any mismatch → fallback.
- **What a fallback loses** is computed from the models (file vs text written): every comment, PI, CDATA
  section, the declaration and DOCTYPE, and every element and attribute in a namespace bpmn-js does not
  know (extensions), unless it was in an element the edit deleted. Verifier round 3 found that `format`
  had only counted comments and PIs it could not place, so extensions and CDATA it dropped went
  unreported; a unit test now forces `format` over kept extensions and requires each to be named.
- **Fallbacks**, each observable (`store.writerStats`, a `rendered` event with `lost`, one terminal note per
  kind and run saying what the save does instead, a warning naming what was lost on **every** save that
  loses something, and with `BPMN_EDIT_DEBUG_WRITES=1` one line per write: `bpmn-edit: debug: write mode=…
  ms=… [lost=n] [reason=…]`):
  - `unbased`: no base known for the disk text → the disk text itself is the base (exact for files
    bpmn-js wrote; otherwise bpmn-js's normalisations are written too, comments etc. still kept), checked;
  - `format`: bpmn-js's output rendered in the file's style with the file's prolog (declaration,
    comments, PIs, DOCTYPE), root start tag (if it declares the same attributes) and epilog (final
    newline); texts bpmn-js has unchanged are written as on disk (CDATA, entity references, comments
    inside them); comments and PIs between elements are put back next to the same element (before the
    next sibling that still exists, else after the previous one, else at the end of the parent). Checked
    to have exactly `out`'s model; what had nowhere to go is listed as lost;
  - `raw`: the disk text cannot be read as XML: bpmn-js's output as it is; its comments, PIs and DOCTYPE
    (found by a plain scan) are listed as lost. `new`: the file is missing or broken, nothing to keep
    (not a fallback).
- **Where the base comes from.** The browser sends `{ type: 'baseline', version, xml }` right after it
  imports a version that may be the file on disk (initial load, change on disk, re-sync, a newer document
  fetched after a conflict), before anything can change the diagram (`saveXML` serialises synchronously
  when called, right after `importXML` resolves; the message goes out before any update based on that
  version). The server looks the version up among the recent versions read from disk
  (`Session#diskTextOf`) and hands `(text, base)` to the store, which keeps it **only while the file
  holds exactly that text** (`store.setBaseline` refuses any other text). After each own write the pair
  becomes `(text written, XML it was written from)` — valid because the check proved the written text
  relates to that XML as the old disk text related to its base. A change on disk replaces the text, so
  an old base can never be applied to new text: until the browser has imported the new version and sent
  its baseline, a write would be `unbased`; in practice every update based on that version comes after
  its baseline on the same socket. A reconnecting page whose document is unchanged re-sends the baseline
  it kept (a restarted host has none).
- **Q2 path unchanged.** Rendering happens in the store's write loop right before `writeAtomically`,
  from the store's own `diskXml` — the same text the pre-write disk check compares the file with, so a
  change on disk still holds the write back and is reported as before. `diskXml`, `lastWrite`, the
  in-flight text, stale-save detection (`looksStale` / `containsChanges` on disk texts) and the
  confirmation of writes over broken files all work on the text written; `saved` reports the XML given to
  `write()` (the session matches it against its accepted updates). Side files keep what they kept before:
  edits that were never written as the editor's XML, a written version (stale save, Ctrl-C checks) as
  the text that was written, i.e. in the file's style. Without `render` (unit tests of the store) the
  store writes the XML as it is.

windows exchange; only the text written to disk differs. The Q4 acceptance criteria (renames, the 40 px
move, information kept, formatting, new elements in the file's style, every write checked, 0 fallbacks on
the structural edits) are met on the whole corpus in all three browsers, for the gestures the E2E and the
verifier's probes cover; the known limits below are where the result is not byte-minimal or falls back.

### Known limits

- `format` is still used when a change cannot be patched in place: a changed text next to an XML comment
  in the same element, changed mixed content, a new element under DI that exists only in bpmn-js's view
  (e.g. a new shape inside a collapsed sub-process of a bpmn-js < 9 file), an element moved together with
  its moved parent, a value normalised on import other than a constant DI offset. It keeps comments and
  PIs next to surviving elements; what it cannot place (e.g. a comment inside a text that changed, or
  next to elements that are all gone) is named in a warning. It also writes bpmn-js's attribute order,
  number spelling and default attributes for that save. Each mode prints its note once per run.
- Comments and PIs inside an element you delete are gone with it (the deletion is the edit); an undo in
  the same run brings them back. The memory is per run of bpmn-edit and holds the last 200 elements.
- Cut and paste writes the pasted element from bpmn-js's output: bpmn-js's copy does not carry
  extensions, and the file's comments/PIs/CDATA in it are not carried over (backlog).
- After an undo, bpmn-js may re-add a reference (`<incoming>`/`<outgoing>`) at the end of its list (the
  file follows: a removed and an added line), and may respell a number in a waypoint it changed during
  the delete and back on undo (a line pair). After a type change and its undo, the DI label bpmn-js
  dropped and brings back is written as bpmn-js has it (e.g. Signavio's `302.0` becomes `302`, its
  `labelStyle` is gone). A restored edge whose `sourceElement`/`targetElement` bpmn-js dropped
  (camunda7-loan-approval) loses those two DI attributes (bpmn-js's model, a line pair).
- In a collapsed sub-process of a bpmn-js < 9 file, bpmn-js ≥ 9 puts the diagram's top-left element at
  (180, 160) on every import, so positions inside it are relative (as in any bpmn-js ≥ 9 tool). Other
  bpmn-js ≥ 9 tools show the labels there displaced (their import does not shift labels).
- Extensions kept on a type change are on disk but not in the open windows' model until the file is
  reloaded (bpmn-js dropped them from the model on replace).
- Element order is not compared (by design: DI order is kept as on disk, new elements go next to their
  nearest sibling); neither are namespace prefixes (only the namespaces themselves).
- The base is trusted as sent by any connected window (host or collaborator); a window can already change
  the whole document. A wrong base is not detected as such: the check proves the result relates to `out`
  as the disk relates to the base.
- Without a base (e.g. an old page, or an update arriving before the baseline) the save is `unbased`:
  correct, but bpmn-js's import normalisations of a foreign file (default attributes, number spelling,
  DI it reorganises) are written in that save.
- The writer runs synchronously on the host (tens of ms for large diagrams).

## S5/S6: presence protocol

### Decision

Presence (who is connected, and from S6 what each window has selected) uses its own message types on
the existing `/ws` socket and never touches the sync messages. Server side it lives in
`src/presence.js`, client side in `web/presence.js`; `src/server.js` and `web/app.js` only forward
messages to it. Palette, name rules and the name generator are in `web/presence-shared.js`, loaded by
both the host and the page, so the colour shown in the list and the selection outline come from one
list.

- A window joins with `hello { name?, color? }` (what its browser has in `localStorage`). The host
  replaces a missing or invalid name with a random friendly one ("Curious Otter") and a missing or
  invalid colour with the least used palette slot, answers `welcome { user }` and broadcasts
  `presence { users }` (the full list, join order) on every join, leave (socket `close`) and `rename`.
  The page stores what it was given, so a reload keeps the name and colour.
- Only connections that said `hello` take part: the user id is the `clientId` from `init`, and other
  clients (tests, older pages) see no presence messages at all.
- Names are cleaned on both sides with the same function (invisible and bidi control characters
  removed, whitespace collapsed, at most 32 characters) and rendered with `textContent` only. A colour
  is a palette index, so no colour value from a client ever reaches CSS.
- The list takes the toolbar's free space between the file name and the save status / Share controls
  and never squeezes names: when they do not fit, the others are shown as colour dots, then the own
  name is hidden ("(you)" stays), then the last users fold into a "+N" entry. The own entry is one
  button (dot, name, "(you)") in every state, so Tab / Enter / Space rename it at any width; after a
  rename started from the keyboard, focus returns to it. "+N" is focusable too (its accessible name
  lists the folded users). The list sits before the status in the markup, so the tab order matches
  the screen.
  Every full name stays in a tooltip. While the own name is being edited, the share link box is
  hidden and the file name narrowed so the field gets at least 120px; Copy and Stop sharing stay.
  Below 720px the link box is not shown at all (Copy copies the link, its tooltip shows it), so the
  toolbar fits down to 640px.
- Invalid presence messages are ignored, not answered with `error`: the editor treats `error` as a
  failed save.
- Collaborators under `/s/<token>/` (S7) take part like any other window: their socket is the same
  `/ws` connection, opened relative to the page. A presence entry is `{ id, name, color, selection }`
  only (clientId, cleaned name, palette index, element ids), so it carries neither the host's file path
  nor the host secret or session token.
- Selection (S6): a window sends `selection { ids }` 50 ms after its selection last changed and only
  if it differs from what it sent last, so the clear-and-restore around every import sends nothing.
  The host relays `selection { userId, ids }` to the others and keeps the latest one per user in the
  `presence` list, so a window that joins later sees it at once. Other windows mark those elements
  with `canvas.addMarker(id, 'remote-sel-<colour slot>')`; the CSS for these classes is generated
  from the palette (shape outline, or the line of a connection, in the user's colour).
- Markers are kept as a wanted state (user -> ids) and reconciled with the canvas after every
  presence message, every import (importXML recreates all elements without markers) and every edit
  (`elements.changed`: deletes, undo). Ids missing from the diagram are skipped and marked once they
  appear (e.g. a task another window created and selected before its update arrived). A window
  never marks its own selection. Two users with the same element selected each add their class;
  where both apply, the later rule in the palette is the one drawn.

### Known limits

- A window is removed when its socket closes. A connection that dies without closing (network loss)
  stayed listed until the host noticed; since S8 the keepalive removes it within 30–60 s, and a page
  that reconnects takes over its old entry at once (see S8).
- Two windows in the same browser share `localStorage`, so they show the same name and colour.
- Colours repeat once more than 8 users are connected.
- A remote marker and this window's own selection on the same element share bpmn-js's outline, which
  then shows the remote colour.

## S7: who may share, and how the secrets are kept

How the security model of `PLAN.md` is implemented (`src/security.js`, `src/server.js`, `web/app.js`):

- **Host secret** (256 bit, base64url) is created at startup and only ever appears in the URL the CLI
  prints and opens, `http://localhost:PORT/?host=<secret>`. The page moves it out of the address bar at
  once (`history.replaceState`, which also rewrites the history entry) into `sessionStorage`, so a reload
  keeps host powers but the secret is not bookmarked, shown on screen or copied with the URL. It is sent
  only to the same origin: in an `X-Bpmn-Edit-Host` header on `/api/share` and as `?host=` on the
  WebSocket URL. Every response carries `Referrer-Policy: no-referrer` (and the page a matching meta tag),
  so neither the secret nor a collaborator's session token leaks to bpmn.io through the watermark link.
  Collaborators never receive it: nothing the server sends contains it, and a socket opened under
  `/s/<token>/` gets no host role even if it presents the secret. A wrong or stale secret simply means no
  host powers (no Share controls, 403 on `/api/share`).
- **Session token** (192 bit, base64url) is created when a tunnel comes up and accepted only while sharing
  is active; Stop sharing (or cloudflared dying) invalidates it at once, closes the collaborators'
  sockets (close code 4001) and stops the tunnel. The next Share gets a new tunnel and a new token.
- **Remote requests** are those with `cf-connecting-ip` or `cf-ray` (the Cloudflare edge always adds
  them and a client cannot remove them; the tunnel connects from 127.0.0.1, so the address cannot be
  used). They are served only `/s/<token>/…` with the current token; everything else, `/api/share`
  included and whatever secret they carry, is 404. `/s/<token>` redirects to `/s/<token>/` because the
  page loads its assets, `api/file` and `ws` relative to itself.
- **Host / Origin check** (DNS rebinding, other web sites): the Host header must be `localhost`,
  `127.0.0.1` or `[::1]` with our port, or the hostname of the tunnel being started or active (421
  otherwise); an Origin, if present, must be one of those as `http://…:PORT` or `https://<tunnel host>`
  (403 otherwise). Both apply to HTTP and to the WebSocket upgrade.
- **No host paths for collaborators**: windows under `/s/<token>/` get the file name only: no absolute
  `path` in `init` or `api/file`, and a failed save is reported as "Could not save <name> on the host's
  machine (<code>)" instead of the file system message (which names the directory). The host's own
  windows keep the full path (tooltip, errors).
- **Tests without Cloudflare**: `BPMN_EDIT_TEST_TUNNEL=fake | rate-limited | rate-limited-once | fail`
  in the CLI's environment swaps in a stand-in provider (`src/test-tunnel.js`) that opens nothing and
  hands out a made-up `*.trycloudflare.com` URL; tests then send the Cloudflare headers to localhost
  themselves. It can only be chosen at startup through the environment, never over HTTP.
- Port fallback also treats a port as busy when another program listens on it on a wildcard address
  (`0.0.0.0` / `::`): macOS lets our loopback binds succeed next to it, but the port is visibly taken.

Known limits:

- Only the tab opened from the printed URL (and its reloads) is the host. A new tab at
  `http://localhost:PORT/` can edit but cannot share; open the printed URL again for that.
- Anyone who can read the terminal output or the process list while the browser is launched sees the
  secret; that is the same user on the same machine.
- Stopping the CLI while a tunnel is still starting does not wait for it: the tunnel module kills
  cloudflared on exit, and a partly downloaded binary leaves a temporary directory in `~/.bpmn-edit/bin`
  (`.cloudflared-*`) that is not cleaned up.

## S8: keepalive, reconnect and the end of a session

Implemented in `src/server.js` (keepalive, close codes, `role` in `init`, `endSession`), `src/presence.js`
(replacing a reconnected page's entry), `bin/bpmn-edit.js` (shutdown order), `web/app.js` (reconnect,
re-sync, overlay) and `web/connection-shared.js` (the numbers below, shared by host and page).

### Keepalive

- The host sends a WebSocket ping to every socket every **30 s** and terminates a socket that has not
  answered the previous ping (pong, or any message) by the next tick, so a dead connection is gone after
  30–60 s. That also removes connections that died without closing from the users list (backlog item from
  S5/S6). `BPMN_EDIT_KEEPALIVE_MS` (hidden, for tests; 0 = off) changes the interval.
- Why 30 s: Cloudflare cuts an idle WebSocket through the quick tunnel after ~125 s (Q3); 30 s leaves room
  for a lost ping and slow networks while adding one small frame per socket and half minute.
- The page also sends `{ type: 'ping' }` every 30 s and expects the `pong` (or any message) before the
  next one; otherwise it drops the connection and reconnects. Browsers do not show WebSocket pings to the
  page, so this is the only way it notices a connection that died silently (Wi-Fi change, sleep, a
  dead tunnel path). Tested with a connection that stops delivering in both directions.
- Real tunnel (`test/e2e/s8-keepalive-tunnel.spec.js`, 2026-10-13, one quick tunnel, default timings):
  a collaborator page opened through the public link stayed idle for **150.0 s** (beyond the 125 s cut)
  on its **first** WebSocket (open 150.4 s, no reconnect, status "Saved"), then renamed a task; the
  host window showed it and it reached disk. A bare WebSocket client on the same link that sent nothing
  at all and only answered the host's pings (5 pings) was **still open after 150.0 s** too: WebSocket
  ping frames alone keep the tunnel's connection open, so the page's heartbeat is not needed for that,
  only for noticing silent deaths. Before S8 the same idle socket was cut after 125.08–125.12 s every
  time (Q3).

### Close codes

| Code | Sent when | Page shows | Reconnects |
|---|---|---|---|
| 4001 `share-stopped` | Stop sharing (S7), to collaborators of that link | overlay "Sharing stopped" — "The host stopped sharing. This link no longer works." | no |
| 4002 `session-ended` | host Ctrl-C / SIGTERM, after the editors flushed their edits (and re-applied them on a last-moment change on disk, Q2) and before the tunnel stops | overlay "Session ended"; collaborators "The host closed this session.", local windows a hint to run bpmn-edit again plus a **Reconnect** button | no (only on Reconnect) |
| anything else (1006, 1001, …) | network, tunnel, killed host process | "Reconnecting…" banner, status "Reconnecting…" | yes |

The shutdown order matters: the host now calls `endSession()` (4002 to every socket, waits up to 1 s for
the close handshakes) before stopping the share, which would otherwise close collaborators with 4001 and
they would read "Sharing stopped" instead of "Session ended". The full order, with Q2's last check of
the file before it, is in Q2, "With reconnect and sharing".

### Backoff and giving up

- Attempts after a drop wait 0.5, 1, 2, 4, 8 s, then 10 s each, ±20 % jitter.
- After every failed attempt the page fetches its own `api/file` (relative to the page, so through the
  tunnel for collaborators): **404** (token revoked, or a restarted host that has no such link) ends the
  session at once ("This link no longer works. Ask the host for a new link."); **530** (Cloudflare has no
  tunnel for that hostname, see Q3) for **10 s** in a row ends it too (a cloudflared reconnect can cause a
  short 530). Anything else (no answer, 200, 502) keeps retrying.
- Otherwise the page gives up once **at least 8 attempts failed and at least 60 s passed** since the drop
  (with the schedule above: after about a minute), "Lost the connection to the host and could not
  reconnect.", with a **Try again** button. Both conditions, so a laptop waking from a long sleep still
  gets its attempts.
- Once given up (or closed with 4001/4002) the page opens no further connection by itself; the E2E tests
  count the page's WebSockets after the overlay.
- If edits could not be saved, the overlay says so ("Your latest changes could not be saved.").

### Re-sync after a reconnect

The new connection's `init` carries the host's current document. The page keeps every edit the host has
not acknowledged (the update in flight when the connection was lost, edits waiting behind it, edits made
while disconnected) and then:

1. the host's document is the one these edits are based on (nobody changed anything meanwhile): the
   current document is sent as it is (also keeps edits that have no op capture, e.g. resize);
2. the host's document is exactly the update that was in flight (accepted, the ack was lost): that update
   counts as acknowledged, the rest is sent;
3. otherwise: the host's document is shown and the edits are re-applied op by op, the same rebase as on
   a `conflict` (Q1). Ops already contained in the document are no-ops (label already set, element already
   created / deleted, and now also a shape already at the moved-to position), so an accepted update is
   not reported as a conflict. Elements others deleted stay deleted; edits of them are reported, as in Q1.

Acknowledged edits not yet confirmed on disk are sorted out first with `init`'s `instance`, `saved` and
`discards` (Q2, "With reconnect and sharing"): those a change on disk replaced while the page was away
are re-applied with the others (case 3).

Versions restart at 1 when the host restarts, so the page forgets its version and takes the one from
`init`. A page whose file has changed identity (another file served on the same port) ends the session
instead of mixing documents.

Presence: each page has a random key (16 bytes, in memory only: a reload or a second tab gets another)
that it sends with `hello`. When a connection says `hello` with a key that an entry of another
connection already has (same role and token), it takes over that entry in place (same position, name and
colour, new id) and the host terminates the old connection. So a reconnect never shows a ghost or a
duplicate, even before the keepalive would notice the old connection. The key is never sent to anyone.

### Host restart

- Ctrl-C: every window shows "Session ended" (above). The host's and local windows offer **Reconnect**.
- After a restart on the same port (Ctrl-C then start again, or the process killed and started again while
  the tab is still retrying), the host's tab reconnects and keeps its edits, but **as a plain local
  editor**: its host secret belongs to the old run, so the host does not accept it (`init` now says
  `role: 'local'`). The page forgets the stale secret, hides Share and says "bpmn-edit was restarted. This
  tab can still edit; to share, open the link printed in the terminal." A stale secret never grants host
  rights (it is compared with the new run's secret only; there is nothing persisted).
- Collaborators of the old run cannot get back in: the old token does not exist in the new run (404 on the
  probe; through the real tunnel the old hostname answers 530). They see "Session ended".

### Known limits

- The page's heartbeat runs on timers, which browsers throttle in background tabs (at most once a minute
  after a while), so a silently dead connection of a hidden tab may take ~2 minutes to be noticed.
- An update refused while the page was away is rebased like any conflict, so the Q1 limits apply
  (unsupported commands that race someone else's edit are dropped, with a notice).
- If the user changed the same label after their accepted update and someone else changed it again during
  the outage, the re-applied (already accepted) label is reported as a conflict, though nothing is lost.
- An oversized update (> 10 MB, closed with 1009) would be retried on every reconnect; with the size limit
  far above real diagrams this is left as is.
- Old collaborator links after a host restart through the real tunnel are ended by the 530 rule (10 s)
  rather than at once.

## S9: what the npm package contains

- `files` in `package.json` whitelists `bin/`, `src/`, `web/` (including `web/vendor/bpmn-js/` with its
  `LICENSE`), `README.md` and `LICENSE` (npm adds `package.json`). Tests, fixtures, `scripts/`, `docs/`,
  `test-results/` and local tool directories are not shipped: 33 files, ~397 kB packed, ~1.2 MB unpacked
  (`npm pack --dry-run`), most of it the vendored bpmn-js build and its font.
- `src/test-tunnel.js` (the stand-in tunnel provider for tests, S7) **is shipped**. `bin/bpmn-edit.js`
  imports it statically, so leaving it out would break the installed CLI at startup. Making the import
  dynamic so the file could be dropped was not worth it: it is 2.4 kB, opens no network connection, and is
  used only when `BPMN_EDIT_TEST_TUNNEL` is set in the CLI's environment (never over HTTP), in which case
  the CLI says "TEST MODE" on stderr. Shipping it also means the E2E suite runs exactly the code users get.
- Hidden, environment-only knobs that ship but are not in the README: `BPMN_EDIT_CLOUDFLARED_URL_BASE`
  (where `cloudflared` is downloaded from; default: the latest GitHub release), `BPMN_EDIT_KEEPALIVE_MS`,
  `BPMN_EDIT_REAPPLY_GRACE_MS` (Q2),
  `BPMN_EDIT_TEST_TUNNEL`, plus the hidden `--write-delay` option.
- Q3 wrap-up: the README states that every Share and every restart gives a new link and that persistent
  links are out of scope for v1 (see Q3 above).

## S10: browser matrix (Firefox, WebKit)

`playwright.config.js` has three projects, `chrome` (Google Chrome, `channel: 'chrome'`), `firefox` and
`webkit` (Playwright's builds, `npx playwright install firefox webkit`), so every spec runs in all three
with no per-test opt-in. v1 support stays Chrome-only; the other two guard against browser-specific
breakage. Still one worker: specs start CLIs on random ports, but several windows per test and
timing-sensitive sync checks were only measured serially.

- Whole matrix: `BPMN_EDIT_SKIP_TUNNEL_E2E=1 npm run test:e2e`.
- One browser: `npx playwright test --project=chrome` (or `firefox`, `webkit`); several projects can be
  given. Combine with a file or `-g` as usual.
- The real-tunnel specs (`s7-share-tunnel`, `s8-keepalive-tunnel`) run in Chrome only, also without
  `BPMN_EDIT_SKIP_TUNNEL_E2E` (Cloudflare rate-limits quick tunnels, so the matrix never starts more).
  Measurement specs stay behind `BPMN_EDIT_MEASURE`.
