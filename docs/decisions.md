# Decisions

Measure-and-decide steps from `PLAN.md`. Each section records the experiment, the numbers, the decision
and its known limits.

## Q1: sync model

### Question

Is full-XML sync (every window sends its whole document after an edit, the host passes it on) good enough
for v1, or does it need operation-level sync? Thresholds from the plan: a lost edit on *different*
elements, or an interrupted in-progress edit in a receiving window, is a defect that must be fixed;
p95 edit-to-visible latency above 500 ms on the large diagram means switching to operation-level sync.

### Experiment

`test/e2e/q1-sync.measure.spec.js` (not part of the regular suite; run with
`LOCAL_BPMN_MEASURE=1 LOCAL_BPMN_MEASURE_OUT=<dir> npx playwright test q1-sync.measure`). It starts the
real CLI, opens 2 or 3 separate Chrome contexts (1280×800) and makes every edit with the real mouse and
keyboard; state is only read with `page.evaluate`. macOS, Google Chrome via Playwright, everything on
localhost.

- Diagrams: the small fixture `test/fixtures/order.bpmn` (7 flow nodes, 6 flows, 5.6 KB) and a large one
  generated by `scripts/gen-large-bpmn.js` (16 rows × 10 columns: 160 tasks, gateways and events plus
  144 sequence flows = 304 elements with DI, 98 KB).
- Latency: one window drags a shape; time from its `pointerup` to the moment the shape's SVG transform
  changes in each other window (MutationObserver, same machine clock). 20 edits per configuration,
  senders in turn.
- Payload: size of the `update` frame sent and the `remote-update` frame received per edit.
- Lost edits: every window edits a different element and the edits are released together
  (`Promise.all` of the mouse-ups / commit clicks) or, for "staggered", window 2 and 3 release at a random
  0–500 ms offset. 10 rounds each of: moves only (simultaneous), moves only (staggered), one window
  commits a label while the others move. An edit counts as lost if the file on disk does not have it once
  every window is saved and idle; windows are also compared with the file ("disagreements"). Any
  notice shown in these rounds is counted as a false notice (the edits never touch the same element).
- Rapid back-and-forth: two windows alternate 6 moves of different shapes, about 100 ms apart, 5 rounds.
- Delete vs edit: window B has the label editor open on X; window A moves Y, then deletes X; B commits.
  3 rounds. Counted: X back on disk ("resurrected"), A's move of Y gone, a notice shown in B.
- Receiver UX, 3 rounds: viewport (B scrolled) and selection (by id) kept across A's edit; B in the
  middle of a drag while A edits (drag still active after 900 ms and B's move saved); B typing in the
  label editor while A edits (editor still open with the typed text and B's label saved).
- "Stuck" counts a window left with a held-back update that is never shown.

The measurement covers moves, label edits and delete-vs-label only. Concurrent create (palette), append
(context pad), connect, delete, drop onto a flow, and the same-element cases are covered by the
deterministic tests in `test/e2e/q1-concurrency.spec.js` (regular suite), not by counts here:
simultaneous moves in 2 and 3 windows; create + append + delete, then connect + rename + move,
released together in 3 windows; rapid alternating moves and renames; an edit of an element deleted
elsewhere; a move of two shapes, one deleted elsewhere; a move re-applied where someone else just drew a
flow; a drop onto a flow re-applied after someone else's edit; a rename or move accepted just before a
concurrent delete; the same label renamed in two windows (one after the other, and released together);
a drag and a label edit in progress while others edit; viewport and selection; the 304-element diagram
with 3 windows; an edit right before a reload. Several tests hold back one window's outgoing updates
(Playwright `routeWebSocket`, like a slow network) to force a given order at the host, including an
update refused twice: moves of two shapes joined by a flow, one re-applied over the other; deleting an
event whose earlier change was already seen (no notice); a concurrent move of an event that is
deleted (notice with the event's name); a connection to, and a move into a sub-process, deleted
elsewhere (notice names the deleted element); the delete notice and a drop onto a flow after two refusals. Each test ends by checking that every window shows exactly the file on disk (ids,
names, bounds, waypoints).

payload are for uncontended edits. After the change, no notice appeared in any of the different-element
rounds (0 false notices in 120 rounds); this was not counted before.

Notes on the numbers:

- About 300 ms of every latency is the client's send debounce (`SEND_DELAY_MS`); serialising, the
  WebSocket hop and the import take ~15 ms on the small diagram and ~70 ms on the large one. p95 on the
  large diagram is 388 ms, below the 500 ms threshold.
- Before, a simultaneous release of edits on different elements lost one of them in every round (the
  host kept whichever full document arrived last). Staggered releases mostly survived because the
  receiving window rebased its unsent edits; rapid alternation lost edits when two updates crossed at
  the host after a rebase restarted the debounce.
- Before, delete vs edit always brought the deleted element back and also undid the deleting window's
  unrelated move: the failed rebase let the editing window's whole document win, with only a console
  warning.
- In the 3-window small run before the change, windows were left showing something other than the file
  in 3 rounds, and 5 times a window kept a held-back update (notice "Someone else edited; shown after
  your edit") for more than 10 s after everything was saved; in that run 3 of the receiver-UX edits never
  showed up in the receiving window within 5 s. (The first attempt of that run aborted on the same
  condition.) None of this occurred after the change.
- An edit that is refused once (see below) becomes visible to the others after one extra round trip
  plus a re-import and re-apply in the refused window; with 3 windows releasing together on the large
  diagram the last edit was visible everywhere within 2 s in every run of
  `test/e2e/q1-concurrency.spec.js` (asserted there).
- Viewport, selection, an in-progress drag and an open label editor were already preserved before
  (S4); they still are.

### Decision

Keep full-XML transport for v1; make the host the single point of serialisation (optimistic
concurrency) and make the client's rebase op-by-op and safe. Latency does not call for operation-level
sync, but the lost edits and the resurrection are defects that had to be fixed.

How it works now:

- Host (`src/session.js`): an `update` is accepted only if its `baseVersion` is the current version.
  Otherwise the host answers `{ type: 'conflict', version, message }` and changes nothing. The one
  exception is a version that only changes made on disk replaced since: such an update is still accepted
  and replaces the document, with a warning, as before (the disk-race policy is Q2's to decide; see the
  known limits for the case where the disk wins instead). Identical content is a no-op whatever its
  base. *Superseded by Q2: a change on disk now counts like another window's update.*
- Client (`web/app.js`): at most one update in flight. Every user action (root command) is recorded as
  an "edit" of id-based ops: label, move, create (palette, paste), append, connect, delete. Each op also
  records what it expects to find (the label before the edit, the position before the move). The edits
  of the update in flight are kept until the host answers. On `conflict` (or when another window's
  document arrives while edits are unsent) the window shows the newer document, re-applies its edits op
  by op and sends the result right away (no new debounce). Because the host refuses any update not
  based on its current version, two updates can no longer cross and overwrite each other.
- Re-applying an op runs bpmn-js behaviours again, against a document that contains other people's
  changes. Two safeguards keep the result equal to what the original command did:
  - Drop onto a flow (bpmn-js splices a shape moved or created onto a sequence flow into it) only
    happens again into the flow the user originally dropped onto; otherwise it is switched off while
    re-applying. Without this, a move re-applied over someone else's new flow spliced the shape into
    that flow, rewired it and deleted two existing flows.
  - Each re-applied op may change the elements its original command changed (recorded from the
    command stack's dirty list), connections attached to them and, for a re-applied drop onto a flow,
    the new second half of that flow. Elsewhere it may only change geometry of connections (re-layout)
    and external labels (bpmn-js repositions a neighbour's label when a flow is re-laid out). Any
    other change (an element created or removed elsewhere, a connection reconnected, a shape
    re-parented or renamed, another shape moved) means the op is undone and reported (`dropped`
    toast, "…could not be applied on top of someone else's edit"). Splicing into and merging of flows
    are structural and therefore still caught.
- Re-applying runs commands that are recorded as edits again; those are replaced by the original
  edits (narrowed to the ops that applied). So an edit keeps what it expects to find (label before,
  position before, the element as the user saw it when deleting, the flow it was dropped onto) no
  matter how often the host refuses the update and it is re-applied; `overrides` are worked out again
  from that original state on every re-apply.
- An op that cannot be re-applied is dropped on its own and the window shows a toast (`#toast`,
  `data-kind="dropped"`), e.g. "Your change to “Ship order” was not applied: someone else deleted it".
  It names the element that is gone: for a connection the missing end, for a move or create the
  container (sub-process, participant) or host it went into, if that is what was deleted.
  The other ops of the same edit and the other edits are kept (e.g. moving two shapes when one was
  deleted elsewhere still moves the other).
- Same element, same property (label text, position): the first update the host accepts wins. The
  window whose op finds the label or position changed by someone else drops that op and shows a toast
  (`data-kind="conflict"`), "…was not applied: someone else changed it first". Different properties of
  the same element (one window renames, another moves) are both kept.
- Delete vs a concurrent edit of the same element: the delete wins. If the edit is still unsent or
  refused, its window drops it with a `dropped` toast ("…someone else deleted it"). If the edit was
  accepted first and the delete is re-applied over it, the deleting window notices that the element
  changed since the user deleted it (position, size or connection ends, and name, noted just before
  the delete command ran) and sends its ids as `overrides` with the update; the host passes
  them on in `remote-update`, and a window that had that element in an accepted update in the last 30 s
  shows a `conflict` toast ("Your change to “…” was undone: someone else deleted it at the same time").
  A delete that is not concurrent (the deleting window had already seen the edit) reports nothing.
  The same applies to connections: a delete notes the connections attached to the element when the
  user deleted it; a connection someone else added meanwhile (append, connect) that the re-applied
  delete removes is reported to them ("Your connection to “…” was removed: someone else deleted it at
  the same time"; `overrides` entry with `kind: 'connection'`). An appended task itself stays.
- Commands without an op capture (resize, bendpoints, replace/change type, colour, lanes/participants,
  …) and undo/redo of edits already sent are recorded as unsupported edits. They are sent normally; only
  when the host refuses that update are they dropped, with a `dropped` toast, after the newer document is
  shown. They never make this window's whole document replace other people's changes. Undo/redo of
  edits not yet sent simply removes / restores the edit, and an unsupported undo cancels its edit if
  that edit is part of the same rebase.
- A remote document arriving while the user drags, has the label editor open or has a popup menu open
  is held back until that ends (notice "Someone else edited; shown after your edit"), then shown with the
  user's edits re-applied. Viewport and selection (by id) are restored after every import.

Why this and not the alternatives:

- Host-side 3-way merge by element id: needs the base version of every client's update, a BPMN-aware
  merge of semantic elements and DI (references between elements, ordering, labels), and conflict
  rules on the host. More code than the client rebase, and most of it would be replaced by a CRDT later.
- Operation-level sync with bpmn-moddle on the host: moves command semantics (layout, behaviours, label
  placement) to Node, which bpmn-js does not provide headless; the host would either reimplement them or
  need jsdom. Latency does not require it (p95 388 ms on 304 elements, dominated by the debounce).
- The chosen design reuses the existing full-XML protocol (one new message type, one optional field), keeps the host a
  dumb, ordered version store, and confines merge logic to the op capture/re-apply that already
  existed. The recorded ops are also the natural input for the Yjs upgrade path in `local-bpmn.md`:
  they are already id-based element operations, the mapping to a `Y.Map` of elements needs.

### Known limits

- Undo history is reset whenever another window's document (or a change on disk) is shown, including
  after a rebase. Undo then only covers edits made since.
- Unsupported commands (above) are lost if they race another window's edit (with a toast). So is an op
  whose re-application would touch other elements than the original did (e.g. a drop onto a flow that
  someone else rewired meanwhile).
- Conflict detection covers label text and position only; ops exist only for the commands listed above.
- Changes on disk racing browser edits (Q2): an update based on a version that only disk changes
  replaced overwrites those changes (warning on the host's stderr and in the browser console). The
  other way round also happens: if a change on disk reaches the host while an accepted browser edit is
  still waiting in the host's write debounce (250 ms), the pending write is dropped (`src/file.js`:
  "a pending save from the editor was discarded"), the disk version is pushed to every window and that
  browser edit is lost, with only the stderr warning. So neither side reliably wins today.
  *Resolved by Q2 (below).*
- Closing, reloading or hiding a window sends a pending edit right away instead of after the 300 ms
  debounce (best effort, `pagehide` / `visibilitychange`); an edit whose update is still waiting for a
  rebase at that moment is lost.
- A window that shows another window's document serialises it itself on its next edit; bpmn-js may
  write the DI elements in a different order than the file had, so `git diff` shows reordered lines that
  carry no change.
- Every edit sends the whole document to the host and from the host to every other window (107 KB per
  edit on the 304-element diagram). Fine on localhost; through a tunnel this is the first thing to
  revisit (diffs, or the Yjs path).
- A window whose edits keep being refused (others editing continuously) keeps rebasing; each refusal
  means someone else's edit was accepted, so the session as a whole always progresses.
- After a re-apply, an edit made of several commands (append = create + connect, paste) is tracked
  under the id of its last command, so undoing only part of it right after a re-apply (before it is
  sent, which happens immediately) is not tracked exactly.
- The client relies on diagram-js internals (`commandStack._currentExecution`, `_stack`, `_stackIdx`)
  to find root commands and undone edits; if they change, every edit is treated as unsupported (safe,
  but concurrent edits are then dropped with a toast instead of merged).

## Q2: browser edit racing a save made on disk (IDE)

### Question

What happens when an edit in the browser and a save of a different change by another program (an IDE)
land within the debounce windows, in either order, or just before Ctrl-C? Is anything lost silently,
and what should the policy be? Product preference: never lose work silently.

### Experiment

`test/e2e/q2-ide-race.measure.spec.js`; method, per-trial data and root causes in
`docs/q2-ide-race.md`. Real CLI, two Chrome windows, the fixture in a temp git repo
(`core.autocrlf=false`), the IDE save simulated by reading the file and writing it back with another
element renamed (`fs.writeFile`). Scenarios: (a) browser edit, then IDE save 0–600 ms later, 15 trials;
(b) IDE save, then browser edit 0–400 ms later, 15; (c) IDE save 20–140 ms before the host writes the
accepted edit, 15; (d) IDE save 0–100 ms before SIGINT while the accepted edit waits for its write,
10 (fresh CLI each).

### Results

| | Before: both kept | Before: lost silently | After: both kept | After: lost (silently or not) |
|---|---|---|---|---|
| a | 2/15 | 13/15 (7 browser edits, 6 disk changes) | 15/15 | 0 |
| b | 11/15 | 4/15 (disk change) | 15/15 | 0 |
| c | 0/15 | 15/15 (disk change) | 15/15 | 0 |
| d | 0/10 | 10/10 (disk change) | 10/10 | 0 |

Before, no loss was shown in any window (the only trace: a stderr warning in 14 of the 42 losses); the
windows always agreed with the file, so everyone converged on the smaller document. Four causes: the
store dropped an accepted but unwritten browser edit when a change on disk arrived; the write loop
wrote over a change the watcher had not reported yet (it waits 150 ms for the file to settle); the
session accepted browser documents based on a version a change on disk had replaced (last write
wins); shutdown cancelled the pending check and flushed over the change.

### Decision

**The change on disk is the newer base; browser edits not yet on disk are re-applied on top of it,
per element, with the Q1 machinery. A true same-element conflict keeps the file's version and is
shown in the window whose edit lost. Nothing is ever written over a change on disk the host has not
seen.** Alternatives considered: last write wins with a toast (still loses work, just visibly);
pause-and-ask (a modal in every window for something that is almost always mergeable, and nobody to
ask at shutdown or when the host's window is not focused); disk always wins (loses browser work).

How it works:

- Session (`src/session.js`): a change on disk is a version like any other: an update based on an
  older version is refused (`conflict`), and the window re-applies its edits on top (Q1 rebase). The
  one exception kept from before: a change on disk that the editor cannot display (`import-failed`)
  can still be replaced by an edit based on the version before it (warning on stderr).
- Pre-write check (`src/file.js`): right before the rename that replaces the file, the store compares
  the file with what it last read or wrote: `stat` (inode, size, mtime) as a cheap pre-check, then the
  content. If another program changed it, the temp file is discarded, the write is held back and the
  change is reported after the usual settle delay, exactly like a change the watcher found first.
  If the file was invalid or missing when last seen, the host may still replace it while it stays
  missing or holds exactly the broken content reported after it settled (as before). Anything else
  holds the write back: a complete BPMN document counts as a change made on disk, other content
  means another program is still writing (e.g. truncated and about to be rewritten), so the host
  waits until the file settles (no stat shortcut in that state).
- Slow saves (`src/file.js`, `confirmMs`, 2 s): a write that replaced a missing or invalid file is
  not reported as saved until the file has held our content for 2 s. The wait restarts with every
  further write of ours and with every missing/invalid observation, and if the file does not hold
  our content when it ends (the other program broke it again), the write stays unconfirmed for as
  long as that lasts (the windows keep the "not valid BPMN" notice). If a valid save arrives while
  unconfirmed (an IDE finishing a slow save from its own copy, without the browser edit), it is
  treated like a change that replaced a pending write: the edits are re-applied on top of it in their
  windows (merged toast), or kept aside if their window has closed. If the host shuts down while
  unconfirmed and the file does not hold our content, flush() keeps it aside (side file + stderr).
- Re-applying is idempotent (`web/app.js`): a label already at its new text, a created element or
  connection already there, a deleted element already gone, and (new) a moved shape already at its
  target position count as applied, with no toast. Before, a change on disk that already contained a
  move (an IDE that reloaded the host's write) gave a false "changed on disk" conflict toast.
- Replacing the file: right before the rename, the store re-stats the file synchronously and checks
  again if it changed while being checked, so the remaining gap is the rename call itself.
- Unwritten accepted edits: when a change on disk replaces a pending write, the session marks the
  disk version with `discardedAfter` (the last version that is on disk). The host also tells the
  windows when versions are on disk (`saved`), so each window keeps the edits of its acknowledged
  updates until then; on a disk version with `discardedAfter` it re-applies its own edits newer than
  that, before its other unsent edits, and sends the result. If some of those edits came from a
  window that has closed since (nobody can re-apply them), the unsaved document is also saved next to
  the file (see Shutdown below for the name), with a stderr warning.
- Browser (`web/app.js`): a change on disk is no longer sent over; it is rebased onto like another
  window's edit. Every window shows "Reloaded from disk" as before; the window whose edits were
  re-applied shows a toast (`data-kind="merged"`): "The file was changed on disk; your edits were
  applied on top of that change". Ops that cannot be re-applied are reported with disk wording, e.g.
  "Your change to “Ship order” was not applied: it was changed on disk at the same time (the file's
  version was kept)" (`conflict`), "…it was deleted on disk" (`dropped`). A delete re-applied over an
  element that was changed on disk says so in the deleting window ("Your delete of “…” removed a
  change made to it on disk").
- Shutdown (`bin/local-bpmn.js`, one added line): after the windows sent their last edits, the host
  checks the file at once (`session.checkDisk()` → `store.checkNow()`, no settle delay). If a change
  replaced unwritten edits, the windows get it, re-apply and send again (second drain, 1 s max) before
  the final write. If nobody re-applied them (no window left, or the drain timed out), or the file
  changes between that check and the final write, the file keeps its content and the editor's
  version is saved next to it as `<name>.local-bpmn-unsaved-<yyyymmdd-hhmmss>.bpmn` (shows up in
  `git status`), with a stderr warning naming the file.

Verified by `test/e2e/q2-ide-race.spec.js` (regular suite): accepted edit + IDE save of another
element (both kept in the file, `git diff` and both windows; merged toast); IDE save inside the settle
delay just before the host write, with the file sampled every 5 ms for 2 s to prove it is never
overwritten (`core.autocrlf=input`); browser edit right after an IDE save; same label in both (file
wins, conflict toast with the exact text, file not overwritten later); Ctrl-C right after an IDE save
(both kept, exit 0); Ctrl-C with no window left (file keeps the save, edit kept aside, untracked in
`git status`); a valid save just before the host write after the file was invalid, and after it was
deleted (both kept); a slow save that finishes after the host wrote a browser edit over the
half-written file (both kept, merged toast); Ctrl-C after the slow save broke the file again (file
left alone, edit kept aside); a save that already contains a move made over a broken file (no false
conflict toast); a save replacing the unwritten edit of a window that
closed (edit kept aside, file keeps the save). The two S3 tests that asserted last-write-wins now assert that both changes are
kept.

### Known limits

- The pre-write check and the rename are separate steps. A save landing between the last check
  (a synchronous stat) and the rename is overwritten, and the watcher then reads our content and
  reports nothing. The gap is the rename call: normally well under a millisecond, but it grows under
  heavy load (before the re-stat was added, a verifier run lost one IDE save in 20 heavily loaded
  "invalid/valid flip" trials this way, with the gap spanning a whole file read).
- A broken file that has been quiet for the settle delay is replaced by the next browser edit, as
  before. If the program that broke it then leaves our content alone for 2 s (`confirmMs`) and only
  afterwards finishes its save from its own copy, that save replaces the browser edit like any save of
  a stale copy: every window reloads it ("Reloaded from disk") but nobody is told the edit is gone
  (verifier: 4/4 with the IDE finishing 2.5 s after the host's write). While the file stays broken
  (or is broken again) the write is not confirmed, so that case is merged or kept aside.
- A save that is valid for less than the settle delay plus the watcher's latency (about 150 ms plus
  a few ms to tens of ms) before the same program breaks the file
  again is never seen by the host. When the host then replaces the broken file it writes its last
  known valid version plus the browser edits, so `git diff` briefly lacks that short-lived save
  until the program saves again (seen in 1–3 of 10 rapid "invalid/valid" flip trials; the final file
  had everything every time).
- With edits in two windows, a window re-applying an op on an element another window created (and
  has not re-created yet on top of the change on disk) is told the element was "deleted on disk";
  the wording is wrong in that case (inferred from the code, not reproduced).
- Edits of a window that closed after its update was accepted but before it was written are not
  merged: the file keeps the change on disk and the unsaved document (all windows' unsaved edits) is
  kept aside, reported on stderr only (no window of its author is left to show a toast).
- A change on disk is merged only where Q1 has ops (label, move, create, append, connect, delete);
  other browser edits racing it (resize, bendpoints, type change, …) are dropped with a toast.
- Conflict detection is per property (label text, position) as in Q1; a change on disk to other
  attributes of an element the browser edits at the same time is kept (the browser op only touches
  its own property), but the browser cannot report it.
- Kept-aside files are never cleaned up automatically; that is deliberate (they are the user's work).
