# Decisions

Measure-and-decide steps from `PLAN.md`. Each section records the experiment, the numbers, the decision
and its known limits.

## Q1: sync model

### Question

Is full-XML sync (every window sends its whole document after an edit, the host passes it on) good enough
for v1, or does it need operation-level sync? Thresholds from the plan: a lost edit on *different*
elements, or an interrupted in-progress edit in a receiving window, is a defect that must be fixed;
p95 edit-to-visible latency above 500 ms on the large diagram means switching to operation-level sync.

### Experiment

`test/e2e/q1-sync.measure.spec.js` (not part of the regular suite; run with
`LOCAL_BPMN_MEASURE=1 LOCAL_BPMN_MEASURE_OUT=<dir> npx playwright test q1-sync.measure`). It starts the
real CLI, opens 2 or 3 separate Chrome contexts (1280×800) and makes every edit with the real mouse and
keyboard; state is only read with `page.evaluate`. macOS, Google Chrome via Playwright, everything on
localhost.

- Diagrams: the small fixture `test/fixtures/order.bpmn` (7 flow nodes, 6 flows, 5.6 KB) and a large one
  generated by `scripts/gen-large-bpmn.js` (16 rows × 10 columns: 160 tasks, gateways and events plus
  144 sequence flows = 304 elements with DI, 98 KB).
- Latency: one window drags a shape; time from its `pointerup` to the moment the shape's SVG transform
  changes in each other window (MutationObserver, same machine clock). 20 edits per configuration,
  senders in turn.
- Payload: size of the `update` frame sent and the `remote-update` frame received per edit.
- Lost edits: every window edits a different element and the edits are released together
  (`Promise.all` of the mouse-ups / commit clicks) or, for "staggered", window 2 and 3 release at a random
  0–500 ms offset. 10 rounds each of: moves only (simultaneous), moves only (staggered), one window
  commits a label while the others move. An edit counts as lost if the file on disk does not have it once
  every window is saved and idle; windows are also compared with the file ("disagreements"). Any
  notice shown in these rounds is counted as a false notice (the edits never touch the same element).
- Rapid back-and-forth: two windows alternate 6 moves of different shapes, about 100 ms apart, 5 rounds.
- Delete vs edit: window B has the label editor open on X; window A moves Y, then deletes X; B commits.
  3 rounds. Counted: X back on disk ("resurrected"), A's move of Y gone, a notice shown in B.
- Receiver UX, 3 rounds: viewport (B scrolled) and selection (by id) kept across A's edit; B in the
  middle of a drag while A edits (drag still active after 900 ms and B's move saved); B typing in the
  label editor while A edits (editor still open with the typed text and B's label saved).
- "Stuck" counts a window left with a held-back update that is never shown.

The measurement covers moves, label edits and delete-vs-label only. Concurrent create (palette), append
(context pad), connect, delete, drop onto a flow, and the same-element cases are covered by the
deterministic tests in `test/e2e/q1-concurrency.spec.js` (regular suite), not by counts here:
simultaneous moves in 2 and 3 windows; create + append + delete, then connect + rename + move,
released together in 3 windows; rapid alternating moves and renames; an edit of an element deleted
elsewhere; a move of two shapes, one deleted elsewhere; a move re-applied where someone else just drew a
flow; a drop onto a flow re-applied after someone else's edit; a rename or move accepted just before a
concurrent delete; the same label renamed in two windows (one after the other, and released together);
a drag and a label edit in progress while others edit; viewport and selection; the 304-element diagram
with 3 windows; an edit right before a reload. Several tests hold back one window's outgoing updates
(Playwright `routeWebSocket`, like a slow network) to force a given order at the host, including an
update refused twice: moves of two shapes joined by a flow, one re-applied over the other; deleting an
event whose earlier change was already seen (no notice); a concurrent move of an event that is
deleted (notice with the event's name); a connection to, and a move into a sub-process, deleted
elsewhere (notice names the deleted element); the delete notice and a drop onto a flow after two refusals. Each test ends by checking that every window shows exactly the file on disk (ids,
names, bounds, waypoints).

Before = full-XML, last write wins at the host, client-side best-effort rebase (commit `55da4f9`).
After = the change described below (final version, including the re-apply safeguards). Latency and
payload are for uncontended edits. After the change, no notice appeared in any of the different-element
rounds (0 false notices in 120 rounds); this was not counted before.

Notes on the numbers:

- About 300 ms of every latency is the client's send debounce (`SEND_DELAY_MS`); serialising, the
  WebSocket hop and the import take ~15 ms on the small diagram and ~70 ms on the large one. p95 on the
  large diagram is 388 ms, below the 500 ms threshold.
- Before, a simultaneous release of edits on different elements lost one of them in every round (the
  host kept whichever full document arrived last). Staggered releases mostly survived because the
  receiving window rebased its unsent edits; rapid alternation lost edits when two updates crossed at
  the host after a rebase restarted the debounce.
- Before, delete vs edit always brought the deleted element back and also undid the deleting window's
  unrelated move: the failed rebase let the editing window's whole document win, with only a console
  warning.
- In the 3-window small run before the change, windows were left showing something other than the file
  in 3 rounds, and 5 times a window kept a held-back update (notice "Someone else edited; shown after
  your edit") for more than 10 s after everything was saved; in that run 3 of the receiver-UX edits never
  showed up in the receiving window within 5 s. (The first attempt of that run aborted on the same
  condition.) None of this occurred after the change.
- An edit that is refused once (see below) becomes visible to the others after one extra round trip
  plus a re-import and re-apply in the refused window; with 3 windows releasing together on the large
  diagram the last edit was visible everywhere within 2 s in every run of
  `test/e2e/q1-concurrency.spec.js` (asserted there).
- Viewport, selection, an in-progress drag and an open label editor were already preserved before
  (S4); they still are.

### Decision

Keep full-XML transport for v1; make the host the single point of serialisation (optimistic
concurrency) and make the client's rebase op-by-op and safe. Latency does not call for operation-level
sync, but the lost edits and the resurrection are defects that had to be fixed.

How it works now:

- Host (`src/session.js`): an `update` is accepted only if its `baseVersion` is the current version.
  Otherwise the host answers `{ type: 'conflict', version, message }` and changes nothing. The one
  exception is a version that only changes made on disk replaced since: such an update is still accepted
  and replaces the document, with a warning, as before (the disk-race policy is Q2's to decide; see the
  known limits for the case where the disk wins instead). Identical content is a no-op whatever its
  base.
- Client (`web/app.js`): at most one update in flight. Every user action (root command) is recorded as
  an "edit" of id-based ops: label, move, create (palette, paste), append, connect, delete. Each op also
  records what it expects to find (the label before the edit, the position before the move). The edits
  of the update in flight are kept until the host answers. On `conflict` (or when another window's
  document arrives while edits are unsent) the window shows the newer document, re-applies its edits op
  by op and sends the result right away (no new debounce). Because the host refuses any update not
  based on its current version, two updates can no longer cross and overwrite each other.
- Re-applying an op runs bpmn-js behaviours again, against a document that contains other people's
  changes. Two safeguards keep the result equal to what the original command did:
  - Drop onto a flow (bpmn-js splices a shape moved or created onto a sequence flow into it) only
    happens again into the flow the user originally dropped onto; otherwise it is switched off while
    re-applying. Without this, a move re-applied over someone else's new flow spliced the shape into
    that flow, rewired it and deleted two existing flows.
  - Each re-applied op may change the elements its original command changed (recorded from the
    command stack's dirty list), connections attached to them and, for a re-applied drop onto a flow,
    the new second half of that flow. Elsewhere it may only change geometry of connections (re-layout)
    and external labels (bpmn-js repositions a neighbour's label when a flow is re-laid out). Any
    other change (an element created or removed elsewhere, a connection reconnected, a shape
    re-parented or renamed, another shape moved) means the op is undone and reported (`dropped`
    toast, "…could not be applied on top of someone else's edit"). Splicing into and merging of flows
    are structural and therefore still caught.
- Re-applying runs commands that are recorded as edits again; those are replaced by the original
  edits (narrowed to the ops that applied). So an edit keeps what it expects to find (label before,
  position before, the element as the user saw it when deleting, the flow it was dropped onto) no
  matter how often the host refuses the update and it is re-applied; `overrides` are worked out again
  from that original state on every re-apply.
- An op that cannot be re-applied is dropped on its own and the window shows a toast (`#toast`,
  `data-kind="dropped"`), e.g. "Your change to “Ship order” was not applied: someone else deleted it".
  It names the element that is gone: for a connection the missing end, for a move or create the
  container (sub-process, participant) or host it went into, if that is what was deleted.
  The other ops of the same edit and the other edits are kept (e.g. moving two shapes when one was
  deleted elsewhere still moves the other).
- Same element, same property (label text, position): the first update the host accepts wins. The
  window whose op finds the label or position changed by someone else drops that op and shows a toast
  (`data-kind="conflict"`), "…was not applied: someone else changed it first". Different properties of
  the same element (one window renames, another moves) are both kept.
- Delete vs a concurrent edit of the same element: the delete wins. If the edit is still unsent or
  refused, its window drops it with a `dropped` toast ("…someone else deleted it"). If the edit was
  accepted first and the delete is re-applied over it, the deleting window notices that the element
  changed since the user deleted it (position, size or connection ends, and name, noted just before
  the delete command ran) and sends its ids as `overrides` with the update; the host passes
  them on in `remote-update`, and a window that had that element in an accepted update in the last 30 s
  shows a `conflict` toast ("Your change to “…” was undone: someone else deleted it at the same time").
  A delete that is not concurrent (the deleting window had already seen the edit) reports nothing.
  The same applies to connections: a delete notes the connections attached to the element when the
  user deleted it; a connection someone else added meanwhile (append, connect) that the re-applied
  delete removes is reported to them ("Your connection to “…” was removed: someone else deleted it at
  the same time"; `overrides` entry with `kind: 'connection'`). An appended task itself stays.
- Commands without an op capture (resize, bendpoints, replace/change type, colour, lanes/participants,
  …) and undo/redo of edits already sent are recorded as unsupported edits. They are sent normally; only
  when the host refuses that update are they dropped, with a `dropped` toast, after the newer document is
  shown. They never make this window's whole document replace other people's changes. Undo/redo of
  edits not yet sent simply removes / restores the edit, and an unsupported undo cancels its edit if
  that edit is part of the same rebase.
- A remote document arriving while the user drags, has the label editor open or has a popup menu open
  is held back until that ends (notice "Someone else edited; shown after your edit"), then shown with the
  user's edits re-applied. Viewport and selection (by id) are restored after every import.

Why this and not the alternatives:

- Host-side 3-way merge by element id: needs the base version of every client's update, a BPMN-aware
  merge of semantic elements and DI (references between elements, ordering, labels), and conflict
  rules on the host. More code than the client rebase, and most of it would be replaced by a CRDT later.
- Operation-level sync with bpmn-moddle on the host: moves command semantics (layout, behaviours, label
  placement) to Node, which bpmn-js does not provide headless; the host would either reimplement them or
  need jsdom. Latency does not require it (p95 388 ms on 304 elements, dominated by the debounce).
- The chosen design reuses the existing full-XML protocol (one new message type, one optional field), keeps the host a
  dumb, ordered version store, and confines merge logic to the op capture/re-apply that already
  existed. The recorded ops are also the natural input for the Yjs upgrade path in `local-bpmn.md`:
  they are already id-based element operations, the mapping to a `Y.Map` of elements needs.

### Known limits

- Undo history is reset whenever another window's document (or a change on disk) is shown, including
  after a rebase. Undo then only covers edits made since.
- Unsupported commands (above) are lost if they race another window's edit (with a toast). So is an op
  whose re-application would touch other elements than the original did (e.g. a drop onto a flow that
  someone else rewired meanwhile).
- Conflict detection covers label text and position only; ops exist only for the commands listed above.
- Changes on disk racing browser edits (Q2): an update based on a version that only disk changes
  replaced overwrites those changes (warning on the host's stderr and in the browser console). The
  other way round also happens: if a change on disk reaches the host while an accepted browser edit is
  still waiting in the host's write debounce (250 ms), the pending write is dropped (`src/file.js`:
  "a pending save from the editor was discarded"), the disk version is pushed to every window and that
  browser edit is lost, with only the stderr warning. So neither side reliably wins today.
- Closing, reloading or hiding a window sends a pending edit right away instead of after the 300 ms
  debounce (best effort, `pagehide` / `visibilitychange`); an edit whose update is still waiting for a
  rebase at that moment is lost.
- A window that shows another window's document serialises it itself on its next edit; bpmn-js may
  write the DI elements in a different order than the file had, so `git diff` shows reordered lines that
  carry no change.
- Every edit sends the whole document to the host and from the host to every other window (107 KB per
  edit on the 304-element diagram). Fine on localhost; through a tunnel this is the first thing to
  revisit (diffs, or the Yjs path).
- A window whose edits keep being refused (others editing continuously) keeps rebasing; each refusal
  means someone else's edit was accepted, so the session as a whole always progresses.
- After a re-apply, an edit made of several commands (append = create + connect, paste) is tracked
  under the id of its last command, so undoing only part of it right after a re-apply (before it is
  sent, which happens immediately) is not tracked exactly.
- The client relies on diagram-js internals (`commandStack._currentExecution`, `_stack`, `_stackIdx`)
  to find root commands and undone edits; if they change, every edit is treated as unsupported (safe,
  but concurrent edits are then dropped with a toast instead of merged).

## Q3: persistent session links across restarts

### Question

Should a shared link survive a restart of the CLI or a new Share (which needs a stable hostname and a
session token that outlives the process), or is a new link per share acceptable for v1? And how quickly and
how reliably does a Cloudflare quick tunnel come up and stay up?

### Experiment

`scripts/measure-tunnel.js` (full write-up and raw logs: `docs/q3-tunnel-measurements.md`,
`docs/q3-tunnel-evidence/`). The real CLI on a copy of `test/fixtures/order.bpmn`, a quick tunnel from
`src/tunnel.js` pointed at it, one GET of `/` every 20 s for 31 min, a WebSocket held open without sending
anything, Chrome loads at start and end; then the tunnel was stopped together with the CLI, the old URL
probed for 2 min, and after 150 s a second CLI + tunnel started on the same file and port. macOS (M1 Pro),
cloudflared 2026.10.0, Chrome 155. Three tunnels in total (one from an independent verification run), no
rate limiting.

### Results

| | |
|---|---|
| Startup, cached binary (spawn → first HTTP 200) | 6479 / 6849 / 7054 ms; ~5–5.6 s of it is cloudflared obtaining the tunnel |
| HTTP over 31 min | 93/93 × 200, latency p95 101 ms, no cloudflared reconnects |
| Idle WebSocket | cut after 125.08–125.12 s every time (close 1006), 14 times in 31 min |
| Old URL after stop | HTTP 530 / Cloudflare error 1033 from the first probe (1.6 s) for at least 2.6 min; the hostname keeps resolving |
| Restart / re-share | a different random hostname every time; nothing points from the old link to the new one |
| Stable hostname | needs a named Cloudflare Tunnel: a Cloudflare account, an own domain on Cloudflare, `cloudflared tunnel login` or a dashboard token, a DNS route |

### Decision

Persistent links are out of scope for v1. A quick tunnel gets a new hostname on every start, so every
Share (and every CLI restart) gives a new link, and the old one stops working at once (Cloudflare error
1033, which local-bpmn cannot customise). The README (S9) has to say so: collaborators need the new link.

Why: the only way to a stable hostname is a named tunnel, which needs the user's own Cloudflare account and
domain plus a browser login or dashboard token, so `npx local-bpmn` cannot set it up for anyone, and the
session token in `/s/<token>` would also have to be persisted across restarts. If ever wanted, it is a
separate opt-in feature (e.g. a `--tunnel-token` option running `cloudflared tunnel run --token`), not
something to block v1 on. Within one run the quick tunnel's HTTP path was stable, which is what v1 needs.

What does have to change, independent of persistent links: an idle WebSocket through the tunnel is cut
after ~125 s, and the page does not reconnect, so an idle collaborator silently stops syncing. The server
must send a keepalive well below 125 s (e.g. every 30 s) and the page must reconnect with backoff and
re-sync; both are handled in S8, with an E2E check that a socket idle for more than 125 s through a real
tunnel stays connected (or recovers transparently). S7 wires sharing up without keepalive.

### Known limits

- The numbers come from one machine on one network over one afternoon; quick tunnels have no uptime
  guarantee ("for testing and development"), and Cloudflare rate-limits their creation per IP (HTTP 429;
  ~5 in a burst locked tunnels out for more than 35 min). The Share UI reports this as such and lets the
  user retry; it never retries on its own.
- Quick tunnels allow at most 200 in-flight requests and no Server-Sent Events (local-bpmn uses neither).
- The 125 s cut is attributed to Cloudflare's proxy read timeout by the matching number only.

## S5/S6: presence protocol

### Decision

Presence (who is connected, and from S6 what each window has selected) uses its own message types on
the existing `/ws` socket and never touches the sync messages. Server side it lives in
`src/presence.js`, client side in `web/presence.js`; `src/server.js` and `web/app.js` only forward
messages to it. Palette, name rules and the name generator are in `web/presence-shared.js`, loaded by
both the host and the page, so the colour shown in the list and the selection outline come from one
list.

- A window joins with `hello { name?, color? }` (what its browser has in `localStorage`). The host
  replaces a missing or invalid name with a random friendly one ("Curious Otter") and a missing or
  invalid colour with the least used palette slot, answers `welcome { user }` and broadcasts
  `presence { users }` (the full list, join order) on every join, leave (socket `close`) and `rename`.
  The page stores what it was given, so a reload keeps the name and colour.
- Only connections that said `hello` take part: the user id is the `clientId` from `init`, and other
  clients (tests, older pages) see no presence messages at all.
- Names are cleaned on both sides with the same function (invisible and bidi control characters
  removed, whitespace collapsed, at most 32 characters) and rendered with `textContent` only. A colour
  is a palette index, so no colour value from a client ever reaches CSS.
- The list takes the toolbar's free space between the file name and the save status / Share controls
  and never squeezes names: when they do not fit, the others are shown as colour dots, then the own
  name is hidden ("(you)" stays), then the last users fold into a "+N" entry. The own entry is one
  button (dot, name, "(you)") in every state, so Tab / Enter / Space rename it at any width; after a
  rename started from the keyboard, focus returns to it. "+N" is focusable too (its accessible name
  lists the folded users). The list sits before the status in the markup, so the tab order matches
  the screen.
  Every full name stays in a tooltip. While the own name is being edited, the share link box is
  hidden and the file name narrowed so the field gets at least 120px; Copy and Stop sharing stay.
  Below 720px the link box is not shown at all (Copy copies the link, its tooltip shows it), so the
  toolbar fits down to 640px.
- Invalid presence messages are ignored, not answered with `error`: the editor treats `error` as a
  failed save.
- Collaborators under `/s/<token>/` (S7) take part like any other window: their socket is the same
  `/ws` connection, opened relative to the page. A presence entry is `{ id, name, color, selection }`
  only (clientId, cleaned name, palette index, element ids), so it carries neither the host's file path
  nor the host secret or session token.
- Selection (S6): a window sends `selection { ids }` 50 ms after its selection last changed and only
  if it differs from what it sent last, so the clear-and-restore around every import sends nothing.
  The host relays `selection { userId, ids }` to the others and keeps the latest one per user in the
  `presence` list, so a window that joins later sees it at once. Other windows mark those elements
  with `canvas.addMarker(id, 'remote-sel-<colour slot>')`; the CSS for these classes is generated
  from the palette (shape outline, or the line of a connection, in the user's colour).
- Markers are kept as a wanted state (user -> ids) and reconciled with the canvas after every
  presence message, every import (importXML recreates all elements without markers) and every edit
  (`elements.changed`: deletes, undo). Ids missing from the diagram are skipped and marked once they
  appear (e.g. a task another window created and selected before its update arrived). A window
  never marks its own selection. Two users with the same element selected each add their class;
  where both apply, the later rule in the palette is the one drawn.

### Known limits

- A window is removed when its socket closes. A connection that dies without closing (network loss)
  stayed listed until the host noticed; since S8 the keepalive removes it within 30–60 s, and a page
  that reconnects takes over its old entry at once (see S8).
- Two windows in the same browser share `localStorage`, so they show the same name and colour.
- Colours repeat once more than 8 users are connected.
- A remote marker and this window's own selection on the same element share bpmn-js's outline, which
  then shows the remote colour.

## S7: who may share, and how the secrets are kept

How the security model of `PLAN.md` is implemented (`src/security.js`, `src/server.js`, `web/app.js`):

- **Host secret** (256 bit, base64url) is created at startup and only ever appears in the URL the CLI
  prints and opens, `http://localhost:PORT/?host=<secret>`. The page moves it out of the address bar at
  once (`history.replaceState`, which also rewrites the history entry) into `sessionStorage`, so a reload
  keeps host powers but the secret is not bookmarked, shown on screen or copied with the URL. It is sent
  only to the same origin: in an `X-Local-Bpmn-Host` header on `/api/share` and as `?host=` on the
  WebSocket URL. Every response carries `Referrer-Policy: no-referrer` (and the page a matching meta tag),
  so neither the secret nor a collaborator's session token leaks to bpmn.io through the watermark link.
  Collaborators never receive it: nothing the server sends contains it, and a socket opened under
  `/s/<token>/` gets no host role even if it presents the secret. A wrong or stale secret simply means no
  host powers (no Share controls, 403 on `/api/share`).
- **Session token** (192 bit, base64url) is created when a tunnel comes up and accepted only while sharing
  is active; Stop sharing (or cloudflared dying) invalidates it at once, closes the collaborators'
  sockets (close code 4001) and stops the tunnel. The next Share gets a new tunnel and a new token.
- **Remote requests** are those with `cf-connecting-ip` or `cf-ray` (the Cloudflare edge always adds
  them and a client cannot remove them; the tunnel connects from 127.0.0.1, so the address cannot be
  used). They are served only `/s/<token>/…` with the current token; everything else, `/api/share`
  included and whatever secret they carry, is 404. `/s/<token>` redirects to `/s/<token>/` because the
  page loads its assets, `api/file` and `ws` relative to itself.
- **Host / Origin check** (DNS rebinding, other web sites): the Host header must be `localhost`,
  `127.0.0.1` or `[::1]` with our port, or the hostname of the tunnel being started or active (421
  otherwise); an Origin, if present, must be one of those as `http://…:PORT` or `https://<tunnel host>`
  (403 otherwise). Both apply to HTTP and to the WebSocket upgrade.
- **No host paths for collaborators**: windows under `/s/<token>/` get the file name only: no absolute
  `path` in `init` or `api/file`, and a failed save is reported as "Could not save <name> on the host's
  machine (<code>)" instead of the file system message (which names the directory). The host's own
  windows keep the full path (tooltip, errors).
- **Tests without Cloudflare**: `LOCAL_BPMN_TEST_TUNNEL=fake | rate-limited | rate-limited-once | fail`
  in the CLI's environment swaps in a stand-in provider (`src/test-tunnel.js`) that opens nothing and
  hands out a made-up `*.trycloudflare.com` URL; tests then send the Cloudflare headers to localhost
  themselves. It can only be chosen at startup through the environment, never over HTTP.
- Port fallback also treats a port as busy when another program listens on it on a wildcard address
  (`0.0.0.0` / `::`): macOS lets our loopback binds succeed next to it, but the port is visibly taken.

Known limits:

- Only the tab opened from the printed URL (and its reloads) is the host. A new tab at
  `http://localhost:PORT/` can edit but cannot share; open the printed URL again for that.
- Anyone who can read the terminal output or the process list while the browser is launched sees the
  secret; that is the same user on the same machine.
- Stopping the CLI while a tunnel is still starting does not wait for it: the tunnel module kills
  cloudflared on exit, and a partly downloaded binary leaves a temporary directory in `~/.local-bpmn/bin`
  (`.cloudflared-*`) that is not cleaned up.

## S8: keepalive, reconnect and the end of a session

Implemented in `src/server.js` (keepalive, close codes, `role` in `init`, `endSession`), `src/presence.js`
(replacing a reconnected page's entry), `bin/local-bpmn.js` (shutdown order), `web/app.js` (reconnect,
re-sync, overlay) and `web/connection-shared.js` (the numbers below, shared by host and page).

### Keepalive

- The host sends a WebSocket ping to every socket every **30 s** and terminates a socket that has not
  answered the previous ping (pong, or any message) by the next tick, so a dead connection is gone after
  30–60 s. That also removes connections that died without closing from the users list (backlog item from
  S5/S6). `LOCAL_BPMN_KEEPALIVE_MS` (hidden, for tests; 0 = off) changes the interval.
- Why 30 s: Cloudflare cuts an idle WebSocket through the quick tunnel after ~125 s (Q3); 30 s leaves room
  for a lost ping and slow networks while adding one small frame per socket and half minute.
- The page also sends `{ type: 'ping' }` every 30 s and expects the `pong` (or any message) before the
  next one; otherwise it drops the connection and reconnects. Browsers do not show WebSocket pings to the
  page, so this is the only way it notices a connection that died silently (Wi-Fi change, sleep, a
  dead tunnel path). Tested with a connection that stops delivering in both directions.
- Real tunnel (`test/e2e/s8-keepalive-tunnel.spec.js`, 2026-10-13, one quick tunnel, default timings):
  a collaborator page opened through the public link stayed idle for **150.0 s** (beyond the 125 s cut)
  on its **first** WebSocket (open 150.4 s, no reconnect, status "Saved"), then renamed a task; the
  host window showed it and it reached disk. A bare WebSocket client on the same link that sent nothing
  at all and only answered the host's pings (5 pings) was **still open after 150.0 s** too: WebSocket
  ping frames alone keep the tunnel's connection open, so the page's heartbeat is not needed for that,
  only for noticing silent deaths. Before S8 the same idle socket was cut after 125.08–125.12 s every
  time (Q3).

### Close codes

| Code | Sent when | Page shows | Reconnects |
|---|---|---|---|
| 4001 `share-stopped` | Stop sharing (S7), to collaborators of that link | overlay "Sharing stopped" — "The host stopped sharing. This link no longer works." | no |
| 4002 `session-ended` | host Ctrl-C / SIGTERM, after the editors flushed their edits and before the tunnel stops | overlay "Session ended"; collaborators "The host closed this session.", local windows a hint to run local-bpmn again plus a **Reconnect** button | no (only on Reconnect) |
| anything else (1006, 1001, …) | network, tunnel, killed host process | "Reconnecting…" banner, status "Reconnecting…" | yes |

The shutdown order matters: the host now calls `endSession()` (4002 to every socket, waits up to 1 s for
the close handshakes) before stopping the share, which would otherwise close collaborators with 4001 and
they would read "Sharing stopped" instead of "Session ended".

### Backoff and giving up

- Attempts after a drop wait 0.5, 1, 2, 4, 8 s, then 10 s each, ±20 % jitter.
- After every failed attempt the page fetches its own `api/file` (relative to the page, so through the
  tunnel for collaborators): **404** (token revoked, or a restarted host that has no such link) ends the
  session at once ("This link no longer works. Ask the host for a new link."); **530** (Cloudflare has no
  tunnel for that hostname, see Q3) for **10 s** in a row ends it too (a cloudflared reconnect can cause a
  short 530). Anything else (no answer, 200, 502) keeps retrying.
- Otherwise the page gives up once **at least 8 attempts failed and at least 60 s passed** since the drop
  (with the schedule above: after about a minute), "Lost the connection to the host and could not
  reconnect.", with a **Try again** button. Both conditions, so a laptop waking from a long sleep still
  gets its attempts.
- Once given up (or closed with 4001/4002) the page opens no further connection by itself; the E2E tests
  count the page's WebSockets after the overlay.
- If edits could not be saved, the overlay says so ("Your latest changes could not be saved.").

### Re-sync after a reconnect

The new connection's `init` carries the host's current document. The page keeps every edit the host has
not acknowledged (the update in flight when the connection was lost, edits waiting behind it, edits made
while disconnected) and then:

1. the host's document is the one these edits are based on (nobody changed anything meanwhile): the
   current document is sent as it is (also keeps edits that have no op capture, e.g. resize);
2. the host's document is exactly the update that was in flight (accepted, the ack was lost): that update
   counts as acknowledged, the rest is sent;
3. otherwise: the host's document is shown and the edits are re-applied op by op, the same rebase as on
   a `conflict` (Q1). Ops already contained in the document are no-ops (label already set, element already
   created / deleted, and now also a shape already at the moved-to position), so an accepted update is
   not reported as a conflict. Elements others deleted stay deleted; edits of them are reported, as in Q1.

Versions restart at 1 when the host restarts, so the page forgets its version and takes the one from
`init`. A page whose file has changed identity (another file served on the same port) ends the session
instead of mixing documents.

Presence: each page has a random key (16 bytes, in memory only: a reload or a second tab gets another)
that it sends with `hello`. When a connection says `hello` with a key that an entry of another
connection already has (same role and token), it takes over that entry in place (same position, name and
colour, new id) and the host terminates the old connection. So a reconnect never shows a ghost or a
duplicate, even before the keepalive would notice the old connection. The key is never sent to anyone.

### Host restart

- Ctrl-C: every window shows "Session ended" (above). The host's and local windows offer **Reconnect**.
- After a restart on the same port (Ctrl-C then start again, or the process killed and started again while
  the tab is still retrying), the host's tab reconnects and keeps its edits, but **as a plain local
  editor**: its host secret belongs to the old run, so the host does not accept it (`init` now says
  `role: 'local'`). The page forgets the stale secret, hides Share and says "local-bpmn was restarted. This
  tab can still edit; to share, open the link printed in the terminal." A stale secret never grants host
  rights (it is compared with the new run's secret only; there is nothing persisted).
- Collaborators of the old run cannot get back in: the old token does not exist in the new run (404 on the
  probe; through the real tunnel the old hostname answers 530). They see "Session ended".

### Known limits

- The page's heartbeat runs on timers, which browsers throttle in background tabs (at most once a minute
  after a while), so a silently dead connection of a hidden tab may take ~2 minutes to be noticed.
- An update refused while the page was away is rebased like any conflict, so the Q1 limits apply
  (unsupported commands that race someone else's edit are dropped, with a notice).
- If the user changed the same label after their accepted update and someone else changed it again during
  the outage, the re-applied (already accepted) label is reported as a conflict, though nothing is lost.
- An oversized update (> 10 MB, closed with 1009) would be retried on every reconnect; with the size limit
  far above real diagrams this is left as is.
- Old collaborator links after a host restart through the real tunnel are ended by the 530 rule (10 s)
  rather than at once.

## S9: what the npm package contains

- `files` in `package.json` whitelists `bin/`, `src/`, `web/` (including `web/vendor/bpmn-js/` with its
  `LICENSE`), `README.md` and `LICENSE` (npm adds `package.json`). Tests, fixtures, `scripts/`, `docs/`,
  `test-results/` and local tool directories are not shipped: 32 files, ~376 kB packed, ~1.2 MB unpacked
  (`npm pack --dry-run`), most of it the vendored bpmn-js build and its font.
- `src/test-tunnel.js` (the stand-in tunnel provider for tests, S7) **is shipped**. `bin/local-bpmn.js`
  imports it statically, so leaving it out would break the installed CLI at startup. Making the import
  dynamic so the file could be dropped was not worth it: it is 2.4 kB, opens no network connection, and is
  used only when `LOCAL_BPMN_TEST_TUNNEL` is set in the CLI's environment (never over HTTP), in which case
  the CLI says "TEST MODE" on stderr. Shipping it also means the E2E suite runs exactly the code users get.
- Hidden, environment-only knobs that ship but are not in the README: `LOCAL_BPMN_CLOUDFLARED_URL_BASE`
  (where `cloudflared` is downloaded from; default: the latest GitHub release), `LOCAL_BPMN_KEEPALIVE_MS`,
  `LOCAL_BPMN_TEST_TUNNEL`, plus the hidden `--write-delay` option.
- Q3 wrap-up: the README states that every Share and every restart gives a new link and that persistent
  links are out of scope for v1 (see Q3 above).

## S10: browser matrix (Firefox, WebKit)

`playwright.config.js` has three projects, `chrome` (Google Chrome, `channel: 'chrome'`), `firefox` and
`webkit` (Playwright's builds, `npx playwright install firefox webkit`), so every spec runs in all three
with no per-test opt-in. v1 support stays Chrome-only; the other two guard against browser-specific
breakage. Still one worker: specs start CLIs on random ports, but several windows per test and
timing-sensitive sync checks were only measured serially.

- Whole matrix: `LOCAL_BPMN_SKIP_TUNNEL_E2E=1 npm run test:e2e`.
- One browser: `npx playwright test --project=chrome` (or `firefox`, `webkit`); several projects can be
  given. Combine with a file or `-g` as usual.
- The real-tunnel specs (`s7-share-tunnel`, `s8-keepalive-tunnel`) run in Chrome only, also without
  `LOCAL_BPMN_SKIP_TUNNEL_E2E` (Cloudflare rate-limits quick tunnels, so the matrix never starts more).
  Measurement specs stay behind `LOCAL_BPMN_MEASURE`.
